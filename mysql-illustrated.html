第 一 讲

一条 SQL 的旅程:服务器层与存储引擎层

MySQL 是"两层楼"的房子:上层的 Server 负责语言(连接、解析、优化、执行、binlog),下层的存储引擎负责存储(InnoDB 的页、缓冲池、redo、undo)。一条查询穿过六站:连接器(认证、权限)→ 查询缓存(5.7 起已删,命中率太低)→ 解析器(词法/语法 → 解析树)→ 预处理器(表列存在性)→ 优化器(按统计信息估成本,挑索引、定 join 顺序)→ 执行器(权限再校验,调 InnoDB handler 一行行取)。

InnoDB 侧还有一层关键机制:数据永远按"页"(16KB)为单位在磁盘与缓冲池 Buffer Pool之间搬运;读一行=找到它所在页,页在内存就是纯内存访问。binlog 在 Server 层写、redo 在引擎层写——两本账怎么对齐,是第 5 讲的主角。

要点追问"为什么查询缓存被删了?"——表结构不常变但数据常变,任何一次更新就得整表失效缓存,高并发写场景下命中率低到不值得维护那把全局锁,8.0 干脆移除。缓存该做在应用层(Redis 那本书呢)。

第 二 讲

B+ 树:为什么这棵树又矮又胖

InnoDB 的索引就是一棵棵 B+ 树。它的设计全围着磁盘 I/O转:数据按 16KB 页读写,一次 I/O 就搬一页。于是——"矮"决定 I/O 次数:节点越大(扇出≈页大小÷指针+键 ≈ 1200 多叉),树越矮,千万级数据树高只有 3 层,查一行最多 3 次 I/O,根页常驻内存实际 2 次;"胖"决定查找方式:非叶子只存键和指针不存数据,一页塞得下几百个分叉;数据全在叶子层,且叶子之间用双向链表串起来——范围查询顺链就走,不用回树。

和老朋友们的分工:哈希表等值 O(1) 但没法范围查询(InnoDB 自适应哈希只是内部加速手段,不承诺);跳表链表式内存友好但磁盘页对指针跳转极不友好(一次随机访问一整个页);红黑树/AVL 二叉、太高,20 层就是 20 次 I/O;二叉搜索树碰上有序插入直接退化成链表。B+ 树用"矮+胖+叶子链表"三重设计统治磁盘索引。

要点"3 层的 B+ 树能存多少行?"——层 1 根 1 页 1200 分叉,层 2 每个分叉 1 页又 1200 分叉,叶子每行按 1KB 算一页 16 行:1200 × 1200 × 16 ≈ 2300 万行,查任意一行 ≤3 次 I/O。这道乘法题就是 B+ 树面试的标准收尾。

第 三 讲

聚簇与二级索引:回表的账,覆盖来平

InnoDB 的表本身就是一棵 B+ 树(聚簇索引):叶子节点放着整行数据,主键选得好坏直接决定表的结构(下一讲第 12 讲看自增与 UUID 的命运差异)。每个二级索引是另一棵独立的树,叶子节点放的不是行,而是主键值。

于是按二级索引查整行,要走两棵树:二级树找到主键,再回聚簇树按主键找行——这就是回表,两棵树的 I/O 一起花。覆盖索引是它的解药:要查的列在二级树的叶子上已经齐了(id + 索引列本身),就不用回表,EXPLAIN 里那行 Extra: Using index 说的就是这件事。所以"只 SELECT 需要的列"不是代码洁癖,是真金白银的 I/O。

回表时注意 I/O 计数:二级树 3 页 + 聚簇树 3 页 = 一次查询 6 次页面访问;而覆盖只花 3 次。这就是"回表是乘法,覆盖是省掉的乘号"。

想一想:为什么二级索引叶子存主键值而不是行数据的指针?——行在聚簇树里会因页分裂搬家,存指针就得维护"搬家协议";存稳定的主键,回表永远从聚簇树根走一遍,结构简单。

第 四 讲

联合索引:一棵树只认一种排序

联合索引 (a,b,c) 的排序规则是先按 a 排,a 相同按 b,b 相同才按 c——像电话簿"姓 → 名"。所以它能加速"姓开头的连续段":a= 能圈出一大段;a= AND b= 在段内继续圈;a=? AND c=? 里的 c 就废了(排序字典里 c 只在 a,b 都定后才有序)。而跳过 a 直接用 b?整棵树无序,只能全扫——这就是"最左前缀"。

更细的边界:范围条件 a>30 AND b=1 里,b 帮不上"继续圈段"的忙(范围之后断前缀);但对覆盖来说 c 列的数据仍躺在叶子上,"扫描 + 过滤(Using index condition / Using where)"还是比回表便宜。下面这棵"排序好的字典",你可以逐条上条件看效果。

要点建联合索引的顺序口诀:等值在前、范围在后;区分度高的靠前;顺手把常查的列排在尾部凑覆盖。order by 也吃最左前缀:WHERE a=? ORDER BY b 能直接沿叶子链表走(无 filesort),WHERE a=? ORDER BY c 就得排了。

第 五 讲

WAL 与两阶段提交:写一条 UPDATE 的完整人生

随机页写是磁盘的噩梦。InnoDB 的答案是 WAL(Write-Ahead Logging):改内存页可以乱,日志必须先行——UPDATE 到来:① 缓冲池里找到页(没有就读进来),直接改,此页变"脏页";② 把"从旧值到新值"的物理事件写进 redo log 缓冲,按 innodb_flush_log_at_trx_commit 决定何时 fsync(=1 每秒安全,=1 每次提交都刷 是默认与最稳);③ 脏页由后台慢慢刷盘。崩溃?重启拿 redo "重放"到最后一页,一行不丢。

但 binlog(归档/主从用)和 redo(崩溃恢复用)是两本账,各写各的会出鬼故事:redo 写完断电,binlog 没写 → 主库有从库无;反过来 → 主库无从库有。MySQL 用两阶段提交对齐:redo prepare → 写 binlog + fsync → redo commit。恢复时以 binlog 为裁判:redo 停在 prepare,查它对应事务的 binlog 完整吗?完整 → 提交;没有 → 回滚。

两个断电结局大不同:停在 prepare 且 binlog 不完整 → 回滚,这条 UPDATE 当没发生;redo 有 prepare + binlog 完整 → 提交它。数据一致性上 binlog 是最终裁判,redo 负责"跑得快",binlog 负责"走得远"。

要点追问"undo log 呢?"——它管回滚与 MVCC:写新值前把旧值记进 undo 版本链,ROLLBACK 沿链倒退,快照读沿链找"我的年代的值"(第 6 讲)。redo 是幂等重放、undo 是逆向补偿,一正一反。两本物理账 + 一本版本账,凑齐 InnoDB 日志天团。

第 六 讲

MVCC:读快照的旅客,不等写字的火车

每行数据背后挂一条 undo 版本链:每个版本记着「值 + 谁改的(trx_id) + 指针」。并发的每个事务分到递增的事务 id。读一行时,拿当前读视图 ReadView(活跃事务清单)沿链找:版本创建者已提交、或就是我 → 用它;还在活跃清单里或比我晚生 → 顺 undo 指针换旧版本,直到遇到"可见"的。读写不再互相阻塞——这就是 MVCC:读走快照,写走当前。

RC 与 RR 的分野只在ReadView 的生成时机:RC 每次 SELECT 都新生成(所以能看见别人刚提交的 → 不可重复读);RR 在第一次快照读时生成、整个事务复用(所以我读到的永远是我进来那刻的世界)。注意:当前读(UPDATE/SELECT FOR UPDATE)不看快照,读最新版本并加锁,更新时还会顺手把本次读到的行"锁成我的"。

第 七 讲

隔离级别:四个档位,三类事故

并发事务交错执行会出三类事故:脏读(读到别人没提交的,人家一回滚你就读了个寂寞)、不可重复读(同一事务内两次读同一行,值变了)、幻读(两次读同一个范围,行数多了/少了——别人插入或删除了几行)。隔离级别就是花钱(并发度)买平安:RU 啥都不防;RC 防脏读;RR 在 InnoDB 里靠 MVCC 快照挡住大部分幻读 + 当前读配 next-key 锁挡住写幻读,基本封盘;SERIALIZABLE 简单粗暴,读也加锁,退化成排队。

第 八 讲

锁与死锁:行锁的三副面孔

InnoDB 的行锁加在索引上,三件套:记录锁锁一行(叶子节点);间隙锁锁两行之间那段空隙——专门防别人往里 INSERT(RR 防写幻读的主力,只在当前读时出场);临键锁(Next-Key)= 记录 + 前间隙,左开右闭区间。UPDATE 走主键等值 → 只上一把记录锁;走非唯一二级索引 → 命中的记录 + 两边间隙都可能被锁住,范围越大锁得越凶。

死锁的标准剧本:两个事务以相反顺序拿两把锁,互相等对方撒手。InnoDB 带死锁检测(wait-for graph,发现环立刻回滚代价小的那个,报 1213);关掉检测就只能靠 innodb_lock_wait_timeout(默认 50s)干等。治本:全库统一"先 A 后 B"的加锁顺序、给热点更新拆队(队列合并)、小事务短事务。

第 九 讲

EXPLAIN:让优化器把底牌亮给你看

EXPLAIN 一行字,三处要盯:type(访问类型的档位,const > 主键 eq_ref > ref > range > index > ALL 全表)、key(实际用了哪棵索引,NULL=没用)、rows + Extra(预估扫多少行、Using where/Using index/Using filesort/Using temporary 这些批注)。慢查询优化第一步永远是:EXPLAIN 看它到底有没有用索引、用哪棵。

索引用不上的经典六连:对列做函数或运算(YEAR(birthday)、id+1=3)、隐式类型转换(varchar 列 = 数字,转的是列!)、LIKE 左模糊('%li' 树无序)、最左前缀断了、OR 两边不同索引(8.0 部分场景可 index merge)、优化器觉得回表比全扫贵主动弃用(低区分度列,比如性别)——最后这条不是 bug,是成本计算。下面工作台,六张牌随便打:

第 十一 讲

主从复制:binlog 的三条运输线

从库挂上主库后,一条 SQL 线程、一条 IO 线程:它连上主库,主库的分发给它线程把自己 binlog 的(文件, 位置)之后的内容源源不断推过来;从库写进 relay log,再由 SQL 线程重放。SHOW SLAVE STATUS 里最该盯的两个数:Seconds_Behind_Master(延迟几秒)和双线程位置差。8.0 主推 GTID(事务全局编号),换主、多源复制不用人肉找位置。

按"什么时候回 OK"分三档:异步(写完 binlog 就走,默认,主炸可能丢);半同步(至少一个从库 ack 收到 relay log 才回 OK——"收到了"不是"执行了");组复制/全同步(多数派落盘才算提交)。另外三个复制格式:statement 记 SQL 原文(可能两边执行结果不一致)、row 记行变化(最稳,体积大)、mixed 让优化器挑。

第 十二 讲

主键怎么挑:自增 ID 与 UUID 的页分裂之战

聚簇索引的叶子就是数据行本身,所以插入位置决定物理布局。自增主键永远"append 到最后一页",一页写满开下一页——顺序写,磁盘的舒适区。UUID 随机落点:一行插进半空的页正中,页放不下就 页分裂:一拆二,两页各半新半旧。分裂后平均利用率只剩 ~65%,随机写让缓存命中率跳水,同一个键空间的二级索引还会跟着连锁分裂——表比自增大出一截,查询多走一层树。

但分布式下自增不够用,折中方案是趋势递增的 ID:雪花算法(Snowflake)时间戳打高位 + 机器位 + 序列号低位,全局唯一又"大方向向前长"。还有一条通用心法:主键要短——它会被复印到所有二级索引的叶子上,越长回表账越贵。

每格 = 一个 16KB 数据页,色带 = 填充率,橙格 = 刚分裂出的半空页

插到 500 行左右再回头看:自增的页几乎全满、总页数≈理论最小;UUID 的页一片橙(半空)。同样装 500 行,多花近一倍磁盘,还让范围扫描多跳一倍页——这就是"主键选 UUID 表膨胀"的现场证据。趋势递增(雪花 ID)就是带着镣铐把随机掰回顺序。
