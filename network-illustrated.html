第 一 讲

封装:每一层只认自己的信封装

数据从应用往下走,每层包一个自己的头(封套子):HTTP 报文 → TCP 段(端口对+序号) → IP 包(IP 对) → 以太网帧(MAC 对+FCS)。两个关键直觉:IP 端到端不变,MAC 逐跳必换——每过一个路由器,二层头重写一次,像快递在分拨中心换面单而收件地址不动;层与层是服务契约:TCP 不在乎底下是以太网还是 Wi-Fi,IP 不在乎谁给自己装帧——分层才能各自演化(所以 HTTP/3 能整体搬去 QUIC/UDP)。

图 1HTTP 报文的下楼与上楼 · 留意换 MAC 不换 IP
TCP 头里 443→52144 端口对全程不变;IP 头 blog(93.1.2.3)↔本机(10.0.0.7)不变;帧头 MAC 从"网关"变"下一跳"。

ARP 彩蛋:每换一跳都要先"吼一嗓子 谁是 10.0.0.1?"拿到新 MAC——这就是为什么抓包分析第一步总先看 ARP。

第 二 讲

三次握手与四次挥手:先对表,再散伙

握手的本质是双向确认"我能发、你能收":SYN(我提议 seq=x)→ SYN+ACK(收到;我提议 seq=y)→ ACK(也收到)。两次不够——服务端无法确认自己的发送+对方的接收这一方向;四次可以但第三次 ACK 常与数据合并,于是省成三次。seq 各自随机(ISN,防旧包串门+防猜序号)。
挥手为什么四步:TCP 是全双工,两条方向各自关门——客户端 FIN,服务端 ACK(我别急,还有货没发完),发完再 FIN,客户端 ACK。最后主动关的客户端进 TIME_WAIT 等 2MSL:① 让最后一个 ACK 可达(丢了服务端会重发 FIN,还能重答);② 让网络里本连接的旧包自然死透,别污染同端口号的新连接。

Flood 剧本:队列打满 → 正常用户 SYN 被丢 → 网站"连不上"。解法三层:syncookies(无状态编码 SYN 进序号)、上游清洗、缩短重试。追问"TIME_WAIT 太多怎么办"——先问为什么短连接这么多(没 keepalive?连接池配错?),而不是先调 tcp_tw_reuse。

第 三 讲

可靠传输:一个丢包的四次抢救

网络只尽力而为,TCP 的可靠靠序号 + 确认 + 重传三件套。ACK 是累积式:"ACK 6" 意为 6 之前我全收了——但如果 5 丢了,后面收得再多也只能重复 ACK 4。第 4 讲的重传演进:① 超时重传 RTO:等定时器到(至少一个 RTT 起)才反应,慢;② 快重传:收 3 个重复 ACK 不等超时直接补发丢的;③ SACK(TCP 选项):告诉对方"5 没收到但 6,7 收到了",精确只补 5,一次到位。QUIC 把这套全部内建且 SACK 更强(每个包的收丢状态可上报)。

dupACK 的本质是"我还在收包,但缺一个"——重复次数暴露空洞;SACK 直接报洞的位置;而超时是唯一"确定失联"的宣告,也是拥塞控制眼里的网络重度拥堵信号(下一讲它要变本加厉地砍窗)。

第 四 讲

拥塞控制:在"探到边"和"别挤爆"之间

丢包是网络的"堵车报告":TCP 据此动态调拥塞窗 cwnd。经典四动作:慢启动不是慢,是每个 RTT 翻倍 exponential 探路(指数);到 ssthresh 转拥塞避免每 RTT +1(加法,AIMD 的 A);丢包则乘法减(Reno 砍半)——AIMD 的公平收敛美点:所有连接同涨同跌。Reno 的 sawtooth 太保守;CUBIC 用三次函数:丢后冲高更快、高位平台更宽(高带宽延迟网络不怂);BBR 掀桌:不等丢包,持续估计链路带宽和 RTT,主动贴着容量跑——但它是"不礼让"的,和 CUBIC 同场要靠配额共存。

图 4cwnd-时间曲线 · 三个算法同一条网络各跑一局(中途丢一次包)
虚线=慢启动门限,红点=丢包时刻

Reno:翻倍→碰线→+1 爬坡→丢包砍半→锯齿永动;CUBIC:砍后不立刻回原位,沿三次曲线先快后慢地拱回去,带宽利用率更高;BBR:一路爬到实测带宽线附近稳成一条马路,几乎不等丢包——三种哲学,"把丢包当信号"还是"把带宽当目标"。

第 五 讲

队头阻塞:一根管子拴死所有请求

TCP 对应用只呈现一条有序字节流——这是 HTTP/1.1 pipelining 和 HTTP/2 多路复用共同的天花板:哪怕应用层拆成 100 个流,丢一个包,后面所有流的数据都得在 TCP 层排队等重传(有序交付语义)。HTTP/2 缓解了应用层队头(帧交错),但传输层队头依旧——一次丢包,100 个 stream 齐卡。QUIC 的破局:把"流"下放到传输协议,每条流独立序号空间独立重传独立交付——丢 3 号流的包,7 号照收;握手还合并了 TLS1.3(0/1-RTT),连接迁移用 Connection ID 不吃四元组(Wi-Fi 切 4G 不断线)。代价:UDP 上重建 TCP 全部可靠性,拥塞控制变成可插拔用户态代码(浏览器可以内置 BBR)。

第 六 讲

HTTP 演进:每版都在省往返

HTTP 是"请求-响应"的语义层,版本史就半部网络演进史:0.9/1.0 一问一答关连接(TTFT 里白送三次握手);1.1 keep-alive 长连接复用 + pipelining 管道(请求可以连着发,但响应必须按序回——应用层队头诞生),外加 Host/Range/Chunked 与一堆缓存头(Cache-Control/ETag 撑起 CDN);浏览器为绕 6 连接上限搞域名分片/雪碧图;2 二进制分帧+单连接多流+HPACK 头压缩,连接数危机解除,但 TCP 队头仍阴魂;2 与 QUIC 合体成 3。状态码三记:3xx 你去哪儿 / 4xx 你错了 / 5xx 我炸了(502 网关探到后端死、504 网关等后端超时——负载均衡时代的两兄弟要能分辨)。

图 6加载 6 个资源:四代连接的排班表

红=建连 蓝=请求 绿=响应。1.0 六次握手排排站;1.1 一条管子串行但省了握手;pipelining 请求连发、响应仍按序(第一块慢拖全场);2 全部交错。这张排班表就是"为什么网页加速从合并域名到 HTTP/2 全在折腾连接"。

第 七 讲

HTTPS:不对称锁门,对称运货

TLS 要解决两件事:把一对对称密钥安全地送到双方手里(对称快但密钥没法裸传),以及证明"对面是 baidu.com 不是路霸"(公钥基础设施 PKI)。流程:ClientHello(随机数 A+套件)→ ServerHello(随机数 B+证书链:站点←中间 CA←根,浏览器内置根公钥逐级验签)→ ECDHE 密钥交换:双方用各自的临时公私钥+两个随机数算出同一把会话密钥——密钥从未上网,且前向安全(私钥日后泄露也解不开旧流量)。之后全是对称的快车道。TLS1.3 的狠活:把 RSA 密钥交换这类旧路删了,只留 ECDHE,握手从 2-RTT 压到 1-RTT,会话恢复 0-RTT(有重放风险,只许幂等首包)。

图 7证书链验签 + 握手时序 · 换张"自签证书"试试

自签剧本:链第一环就验不过(没有受信 CA 的签)——浏览器弹红色警告,不是"不安全"而是"无法确认他是谁"。中间人攻击的成本=骗过 CA 或让用户装根证书,这也是企业代理能解密流量的原因(它成了你信任的 CA)。

第 八 讲

DNS:一次问路的接力

你的机器只问了本地解析器(recursive,替你把事办成),但解析器自己要走迭代路:问根(不答,指 .com)→ 问 .com(不答,指权威)→ 问权威(答 A 记录)。层层都是"我只知道下一步该问谁"。缓存策略撑起了这套系统不崩:TTL 决定每层能记多久,负缓存(NXDOMAIN)同样有 TTL;这也是 DNS 切换慢的原因——改记录只是源头变了,全网还得等各缓存过期(提前调低 TTL 是迁站第一课)。记录家族:A/AAAA、CNAME(别名,链的尽头还得 A)、MX、TXT(域名验证/SPF)、NS、SRV。DNS 的软肋:明文 UDP(可窃听可投毒)、慢路径(首次解析几百 ms)——催生了 DoH(HTTPS 里问)/DoT,以及 HTTP/2 push 时代的 EDNS client-subnet… 还有 GFW 的众所周知章节。

图 8问路动画 · 递归的委托与迭代的跑腿

冷缓存四跳;热缓存一跳直返(浏览器/OS/解析器层层皆 cache)。TTL 那题:新请求按旧 TTL 分布被旧 IP 黏住——迁移前先把 TTL 调小,发布完再调回,这是运维的肌肉记忆。

第 九 讲

身份四件套:Cookie·Session·JWT·SSO

HTTP 本身无状态,身份是后来"贴"上去的。Cookie:Set-Cookie 存浏览器,同源请求自动携带(HttpOnly 防脚本偷、Secure 防明文、SameSite 防 CSRF——三件套背全)。Session:服务端存会话,Cookie 只带 session id——水平扩展就遇到"会话在哪台机器":粘滞会话(IP hash)→ 中央会话(Redis,主流)→ 干脆无状态:JWT,把身份自包含进令牌(header.payload.signature),任何节点拿公钥就能验签,不用回中心问——代价是吊销难(短过期 + 黑名单补救)、payload 别放敏感料(Base64 不是加密,现场点一下"篡改"就懂)。SSO=多应用共享一次登录:中心域发全局会话,子系统换发自己的票(OIDC/CAS 流派)。

第 十 讲

排障:把"慢"拆成时间轴

"网站好慢"永远要先拆段:curl -w @fmt 或浏览器 Performance 面板把一次请求切成 DNS → TCP → TLS → TTFB(服务端) → 下载。哪段红查哪:DNS 慢→换 local resolver/预解析;连不上→安全组/路由/队列满;TLS 慢→证书链没带全(要再下载中间证书!)、握手 2-RTT;TTFB 高→服务端/DB/缓存,与网络无关;下载慢→带宽/分片/TLS record size。工具阶梯:ping(通不通+RTT)→ traceroute/mtr(路径断在哪跳)→ dig(解析对不对)→ curl -v(握手细节全露)→ openssl s_client(证书链体检)→ tcpdump(终极显微镜)。面试标准句:"先分段定位,再谈优化"。

图 10一条真实投诉的时间轴 · "打开商品页要 3 秒"

案一:TTFB 2.4s 一家独大 → 网络无罪,去查缓存穿透(Redis 那本第 7 讲等你)。案二:TLS 段红 → 服务器没下发中间证书,浏览器自己跑去找 CA 补链——"curl 快浏览器慢"的经典错位。时间轴不骗人,玄学才骗人。
