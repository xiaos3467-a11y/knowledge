设计模式
图解讲义

23 个模式不是背诵清单,是23 个"被重复发现的解法"。这张宫格每块都能点开:它解决什么问题、在 JDK/Spring 里以什么身份生活。先建立地图,再进样板间。

序模式宫格 · 创建 5 · 结构 7 · 行为 11
点任意一个模式。

学模式的正确姿势不是"找地方套用",而是先认痛点:哪段代码让你改了 A 必须动 B?哪种对象创建散落五处?痛处对上一个模式名,它带着几十年的成熟方案来找你——这册的每道"装修实景"都从痛点开门。

第 一 讲

策略模式:把"变的部分"装进格子

支付要支持信用卡、借记、积分……朴素写法是 if-else/switch 金字塔:每加一种方式,都要回到主流程动刀,回归测试从头跑。策略模式:把"算法族"各自封装成实现同一接口的类,运行时从策略表(Map)按 key 取——主流程从此不为新增而改动(开闭原则)。但注意模式自身的演化:老式"工厂+抽象策略"要你手动注册;if-else 只有三五行时它反而是坏味道——策略模式的甜点区是"分支多、会变、每支都有独立逻辑"。Spring 给了现代化写法:注入 Map<String,PayStrategy>(bean 名即 key)或 List<Strategy> 按 supports() 匹配——注册表由容器维护。

图 1"新增加密货币支付" · 两种代码各要动几行?diff 见真章
if-else 世界
public BigDecimal pay(int way, BigDecimal amt) { // 主流程 = 所有策略的坟场 if (way == CREDIT) return credit(amt); else if (way == DEBIT) return debit(amt); else if (way == POINT) return point(amt); return reject(amt); }
策略表世界
Map<Integer, PayStrategy> table; public BigDecimal pay(int way, BigDecimal amt) { return table.get(way).pay(amt); // 永远这一行 }

点新增:左边主流程被切开动刀(新分支插入 + 回归测试范围=全部),右边主流程零 diff,新增=新文件+注册一行——改动半径决定爆炸半径。追问"那策略只有 3 行分支呢?"——诚实答案:别上模式,if-else 挺好。

第 二 讲

装饰器:给对象一层层穿外套

想给输入流加上"缓冲 + 解压 + 行号"三种能力,排列组合用继承写:4 种能力 = 16 个子类——继承是编译期的静态组合,爆炸不可控。装饰器把"增强"变成运行期的洋葱:每层持有对同接口的包装对象,自己加一点料再把活转给内层。JDK 的 IO 家族就是教科书:new BufferedReader(new InputStreamReader(new GZIPInputStream(file)))。同族思想在框架层随处可见:Spring 的 BeanPostProcessor 链、Retryable/Hystrix 式包装、Servlet Filter——凡"能力自由组合+可插拔",想想到装饰器。代价:栈深了调试栈满屏 wrapper,对象身份靠 equals 包装链穿透。

图 2字节流过洋葱 · 勾选外套,放一坨数据进去
顺序也有意义:解压必须在缓冲内侧还是外侧?

数据每过一层被加工一次——继承组合数 2ⁿ,装饰器组合数 n 层自由拼。"顺序题"答案:Gzip 包 File、Buffered 包 Gzip(先解压再缓冲读),包反了就是乱码事故——洋葱圈层序,是装饰器唯一的深坑。

第 三 讲

单例的七种写法,和三种进攻

看似最熟的模式,翻车最多的也是它。朴素饿汉在并发下"检查-加锁"之间被插队造出两个;双检锁(DCL)修了竞态,但 instance=new Singleton() 是"分配内存→初始化→赋值指针"三步——无 volatile 时后两步可重排,另一线程第一重检查拿到"非 null 但半成品"(第 3 册 volatile 与 DCL 的账,在这结账);静态内部类用 JVM 类初始化锁拿到懒加载+线程安全+免 volatile;枚举是 Effective Java 的冠军——序列化与反射攻击都免疫(反射调私有构造器会拿到"第二个枚举",但 JDK 对枚举构造器直接抛异常)。更重要的是知道什么时候"别用单例":隐藏依赖让测试举步维艰,它是全局变量的化妆舞会。

图 3单例擂台 · 选写法,放三种攻击

五种写法定格在擂台:并发双线程、反射私构造、序列化 clone 三把刀轮流砍。全绿的只有枚举;静态内部类会漏过序列化刀(不实现 Serializable 时)但倒向反射。而 Spring 的 @Bean 单例是第六种容器托管式——注册表单例池(singletonObjects),它的"唯一性"由容器的双检锁保证,出了容器就作废——这也是"为什么 Spring 不用 DCL 枚举"的答题点。

第 四 讲

观察者:一处变更,广播全场

下单成功要：加积分、发短信、推数仓。直调版=OrderService 认识全世界,加一个下游就改一次上游;观察者版=发布一个事件,谁关心谁订阅。依赖方向从此掰正(上游不认识下游,合依赖倒置)。三个必修细节:① 弱引用注册表(否则被观察者永生——Java 监听器内存泄漏的经典款);② 通知线程语义(Spring 默认同线程同步,RxJava 靠 scheduler 切);③ 事件风暴与顺序(@Order/分区)。它的现代放大版遍地都是:Spring Event、MQ 发布订阅、前端 Redux、Vue 响应式——全是"发布者-订阅者"这一个骨架的不同肌肉。

图 4强直调 vs 订阅广播 · 加第 4 个下游时看谁改上游

广播版:新下游=新订阅者文件,上游零改动;直调版每次都是"核心类开膛日"。这也正是第 6 册 Agent 事件总线、Kafka 发布订阅的设计母型。

第 五 讲

责任链:给请求修一条关卡路

请求过一道道关卡:鉴权→限流→参数校验→业务——每关可选放行/拦截/改道,下一关不知道上一关是谁。把"处理器序列"从硬编码嵌套 if 变成可插拔的链:Servlet Filter 链、SpringMVC HandlerInterceptor、Netty ChannelPipeline、Dubbo 过滤器簇、审批流引擎,全是它。链的三要素:节点契约(process/handle)、传播方式(next.handle 或 fire 语义)、装配权(谁决定顺序——这往往才是架构设计本身:限流放鉴权前省算力,还是鉴权前限流放前面防越权探测?)。它的兄弟是拦截器/AOP:同一条链的不同装配时机。

每种请求沿链走到哪关停一目了然。顺序哲学题:把"限流"挪到"鉴权"前=省算力但匿名流量也能打到业务校验;挪后面=先验明正身再按用户配额——两种都对,取决于你防的是误伤还是恶意,这正是责任链真正的设计点。

第 六 讲

代理:替身文学的一千种面孔

控制对目标的访问,顺便塞横切——这就是代理。静态代理(手写包装类,每个接口成员手写转发,累);JDK 动态代理(运行时生成接口实现,InvocationHandler 统一收口——RPC 客户端存根、MyBatis Mapper 的"没有实现的接口"全靠它);CGLIB(生成子类覆写方法,类无接口时的方案)。按意图分:远程代理(Dubbo 把网络调用伪装成本地方法)、虚拟代理(图片懒加载、JPA 的 @OneToOne lazy)、缓存代理、保护代理(权限)、智能引用(计数)。第 3 册 AOP 那一章把"事务/日志是动态代理的产物"讲透了,这里换个视角:代理是"面向接口编程"吃到红利的那一半——正因为调用方只认接口,替身才有资格上岗。

图 6一个调用的三层替身 · 点播放看横切堆栈

调用方以为在调真身,其实一路穿过 权限代理→缓存代理→(RPC 时:网络代理)→ 真身。每层只认识接口不认识"下家是谁"——这是代理与装饰器唯一的实质差异:装饰器重在"加能力",代理重在"控访问",结构同形、意图相反。

第 七 讲

建造者与原型:造的姿势与抄的姿势

建造者治"重叠构造器":15 个可选参数 = 2¹⁵ 个重载的坟;builder 链式只喊你在意的,且不可变对象一次成型(build 后无 setter,线程安全)。现代 Java:Lombok @Builder、record + withX。原型治"昂贵对象的重复装配":clone 一份再改——但 Object.clone 是浅拷贝:外层字段逐个赋值,数组/集合/嵌套对象的引用原样照抄——两个"独立"对象共享同一个内部 List,改一个崩两个(面试陷阱+生产事故双料)。真深拷贝:序列化往返/手写 copy 构造器/Apache Commons。Spring 的 scope=prototype 不用 clone,而是把 BeanDefinition 再走一遍工厂——"原型"模式的工业化改名。

第 八 讲

模板方法·适配器·工厂速通

三件套一句话档:模板方法——流程钉在父类、步骤留给钩子(比策略"重":编译期骨架;JdbcTemplate.execute 把"拿连接/释异常"固定,StatementCallback 留白;Spring Bean 生命周期本身就是给业务的大模板);适配器——目标接口(客户端想要的)与被适配者(已有的)不兼容时的转接头:Arrays.asList、InputStreamReader、DDD 防腐层的本质就是架构级适配器;工厂家族——简单工厂(工具方法,违反开闭)→工厂方法(一个产品一个子类,开闭达成)→抽象工厂(产品族:换一家=UI/存储/主题成套换)。当"new 什么"成为会变的决策,就把它锁进工厂——Spring IoC 容器是工厂模式+注册表的终极工业化:全应用只留一个"决定 new 什么"的地方。

模板 vs 策略:骨架继承复用(编译期、整体流程)vs 组件组合注入(运行期、单点算法)——Spring 生态整体趋势:模板方法在新框架里越来越少被直接继承,取而代之是回调与自动配置。

第 九 讲(终)

模式的反面:没有模式的场景别硬套

GoF 原文最后一章就写着"模式如何慎用"。模式是"反复出现的痛点的解法总结",不是"炫技的题库"。三条反模式清单:① 预防性抽象:只有一个实现就造接口+工厂+策略"以后好扩展"——扩展点要长在真实变化上,猜的变化九成猜错(YAGNI);② 模式崇拜的重型工厂链:读三屏才找到真正干活的那行代码;③ 把语言特性当模式用:Java 9+ 用 var/record/密封类可能让某些"经典模式"退化——策略≈函数对象(Comparator.comparing)、单例≈枚举、命令≈lambda、观察者≈Flow API。现代框架已经把模式消化成默认结构:你用 Spring 就已经在模板方法(IoC 容器)+代理(AOP)+工厂(BeanFactory)+观察者(event)的样板间里生活。认模式是为了读框架源码快,写业务代码时,先写直白的 if,直到它真的疼——这就是本册的毕业寄语。
