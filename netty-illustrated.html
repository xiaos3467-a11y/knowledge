十讲 · 高性能网络框架的底座

Netty
与 IO 模型

十万连接为什么轮不到"一线程一 socket"?答案全在怎么知道哪个 fd 就绪了。先把 select 和 epoll 的差别看成一遍动画——这是理解 Netty 一切设计的前提。

序8 个连接,3 个有数据 · select 挨个问,epoll 直接摘
select/poll:每轮全量拷贝 + 挨个扫
epoll:注册一次,就绪回调,只交名单
两侧扫描轮数、拷贝成本自己说话——fd 越多,左边的代价越离谱(O(n) vs O(1))

左边:每次调用要把 fd 集合拷进内核、全表过一遍,10 万连接 1 个就绪也要问 10 万次;右边:epoll_ctl 注册一次,谁就绪内核记在就绪链表,epoll_wait 直接把名单摘回来。Java 的 Selector 在 Linux 上底层正是 epoll(LinuxEPollArrayWrapper)——Netty 干脆写 native transport 连"数组中转"都省了。

第 一 讲

IO 模型族谱:两个维度五张牌

先拆两个正交维度:等待数据时你干什么(阻塞/非阻塞/被人叫醒)和数据拷到你手里谁动手(内核拷=同步,你直接拿到 DMA 的地址=异步)。五张牌:① 阻塞 IO——睡到数据就绪且拷好;② 非阻塞 IO——反复"有了吗?没有…没有";③ IO 多路复用——在 select/epoll 门口睡,多家 fd 谁亮办谁(单线程管万连的秘密);④ 信号驱动——就绪了内核发信号喊你(用得少);⑤ 异步 IO(AIO)——"读好了直接把地址给我"(Linux 上实现长期拉胯,Netty 也基本只玩 ③)。Java 的 NIO = ③;Netty = ③ 的工程天花板:epoll + EventLoop + 无锁串行化。

等待阶段数据拷贝典型
阻塞 IO全程睡同步(内核拷你等)BIO 一连接一线程
多路复用睡在 epoll_wait(可多 fd)同步(就绪后自己 read)Netty/Redis/Nginx
AIO不等(回调/Future)内核拷完通知你Windows IOCP;Linux 成色一般

第 二 讲

NIO 三件套:Channel / Buffer / Selector

NIO 的语法三件套:Channel(双向管道)、Buffer(读写都经它,三个指针位置/界限/容量)、Selector(epoll 的对象化)。最反直觉的是 Buffer 的"翻面舞步":写入后必须 flip() 才能读,读完 clear() 或 compact() 复用——position/limit 的小剧场演一遍就再也不忘。Netty 的 ByteBuf 改进:读写各有指针(readIndex/writeIndex,不用 flip)、动态扩容、引用计数、池化。

图 1Buffer 三步舞:put → flip → get → compact
pos limit cap
初始:pos=0 limit=cap(写满为止)

写阶段 limit=容量门、pos 是笔尖;flip 后"笔尖归零、门收到墨迹尽头",读只能读到写过的位置——把刚写的字递出去读,就这么两步。Netty 双指针把 flip 免了,这是它比原生 NIO 好用的第一处。

第 三 讲

EventLoop:一个线程、一个 Selector、一条无穷环

Netty 的心脏:一个 EventLoop = 一个线程 + 一个 Selector + 一个任务队列,while(true) 转三件事——① select(本轮有网件事吗);② 处理就绪事件(read/write/accept/connect,全部在这个线程串行跑);③ runAllTasks(执行 submit 进来的普通任务,限时限量,IO 永远优先)。「一个 Channel 终生绑定一个 EventLoop」是它的铁律:同一 Channel 的所有事件都在同一线程,handler 里没有竞态、不用加锁——这叫无锁串行化设计(对比:actor 模型)。代价:绝不能在 handler 里干阻塞事(DB/大计算)——一堵全组线程陪葬,重活丢给业务池(pipeline.addLast(bizGroup, handler))。

转起来看配额:每圈 IO 先吃,任务最多干一小段(defaultRatio=55 意味着 IO 预算约 45%)——网件永远不被任务饿着。按"阻塞"键:整环卡死,这个 EventLoop 上所有 Channel 一起瘫痪——"handler 别阻塞"不是建议是律法。

第 四 讲

Pipeline:进站一条河,出站一条河

Channel 的责任链:入站事件(读、连接、异常)从 head 流向 tail 过一遍 InboundHandler(解码→聚合→鉴权→业务),出站(写、关闭)从触发者流向 head 过 OutboundHandler(编码→加密→flush)。方向不同,经过的节点不同——中间业务 handler 之后的 inbound 节点,出站事件压根不经过。handler 三原则:① @Sharable 才跨 Channel 复用(有状态 handler 必须 per-connection 一个,比如拆包器);② 传播靠 ctx.fireXxx / ctx.write,忘了调=链到此断(经典 bug:handler 没转发事件,后面全收不到);③ ctx.write 从当前节点向 head 走,会再遇出站 handler,channel.write 从 tail 走全程——重复编码事故之源。

图 3六个节点两条河 · 点"来包了"和"回话了"
入站蓝,出站黄。留意写方向从哪个节点开始。

典型排布:head → ssl → aggregator(拆包) → codec(解码) → auth → biz → tail。"忘了 fire"版本:包停在第 4 站——业务收不到请求且毫无报错,新人踩坑率最高的 Netty 事故。

第 五 讲

ByteBuf:引用计数是把双刃剑

池化内存(默认 PooledByteBufAllocator,jemalloc 式 arena/chunk/page 三级)是 Netty 高性能的钱袋子;代价是手动记账:每块 ByteBuf 带 refCnt,retain+1 / release-1,归零才回池。规则只有一条:谁最后拿到,谁 release——出站消息 write 成功后由 Netty 自动释放;入站消息传到业务链末端必须你释放(尤其被聚合器拆过的切片,用的是 derived buffer,父内存块靠引用计数撑到最后一个 release)。忘了 release=堆外内存慢慢见底,排查看 -Dio.netty.leakDetection.level=PARANOID,它会打采样栈告诉你哪行代码拿了没还。

refCnt 归零→内存回池,再碰它就是 IllegalReferenceCount 或者更坏:数据被覆写后的静默脏读(比 NPE 阴险十倍)。入站对象在 @ChannelHandler.Sharable=false 的异步业务池里跨线程用?先 retain,用完 release——顺序错一步就是事故。

第 六 讲

零拷贝四式:数据不搬家,只换路

"读文件发 socket"的朴素写法:DMA 进内核缓冲 → CPU 拷到用户态 → CPU 再拷回 socket 缓冲 → DMA 进网卡——4 次拷贝 2 次上下文切换,数据在内存里折返跑。四式省它:① mmap+write:用户态只拿映射地址,省第一次 CPU 拷贝(还能改);② sendfile(transferTo):数据全程不出内核,网卡走 scatter-gather 直接从内核缓冲 DMA——2 次 DMA 0 次 CPU 拷贝,Netty 的 FileRegion 就是它;③ 池内逻辑零拷贝:Unpooled.wrappedBuffer(header,body) 合成 CompositeByteBuf 一次写出、slice() 切视图——不搬一个字节,只拼描述;"零拷贝框架"说的多是这第三式+②的组合拳;④ Direct Buffer:堆外分配,IO 时省 Java 堆→native 的隐式复制,配合池化摊掉分配成本。

图 5同一段文件发上网:朴素路与 transferTo 路

高亮箭头=正在发生的拷贝。要改内容才需要第三式的合并;纯转发(文件服务、网关)sendfile 一步到位——HTTPS 时代 sendfile 优势缩水(反正要用户态加密),但对 RocketMQ/Kafka 这类"页缓存+发送"架构仍是命根。

第 七 讲

粘包拆包:TCP 是水流,消息要自己数着喝

TCP 只保证字节流有序,不保证"一次 read 正好一条消息":可能两条挤一包(粘),也可能半条先到(拆)。对策从笨到聪明:定长(浪费)、分隔符(内容含分隔符就寄,如换行协议)、消息头带长度字段(工业标准):读满 header→取 len→等齐 len 再交下游。Netty 把第三式做成积木:LengthFieldBasedFrameDecoder(7 个参数描述"长度字段在哪、占几字节、要不要加上自己的长度、跳过长 header 之外还有什么"),外加 LineBased/Delimiter 两小块便利贴。拆包器必须 per-channel 一个(有内部缓冲,不能 @Sharable)。

图 6三条消息漂成一串字节 · 定长 vs 长度字段两种喝法
发送方发出:"LOGIN|ab"(6B)、"HI"(2B)、"BYEBYE|9"(8B),每条前加 1 字节长度。

固定读:第 2 条从消息中间切开——上游拿到"假消息",协议越读越乱(漂移是致命病)。长度字段:先啃下 1B 头知道"后面 6 条",凑齐才 fire 一条——把"消息边界"从祈愿变成算术。HTTP 的 Content-Length 同理,chunked 是分块变体。

第 八 讲

心跳:没有它,连接是薛定谔的连接

TCP 自己不会告诉你"对面进程死了但机器还活着"(FIN 发不出)、中间 NAT/防火墙悄悄掐了会话。所以应用层必须定期嘘寒问暖:Netty 给尺子 IdleStateHandler(readerIdleTime, writerIdleTime, allIdle))——读/写/全空闲到点触发 UserEvent,你的 handler 收到就:客户端发心跳包;服务端连续 N 次没见任何字节→close(回收半开/死连接,不然 fd 泄漏)。双向都要:服务端也有"我不说话了"被踢的时候。心跳频率=故障发现时间×可承受的误杀率折中;配合断线重连指数退避+随机抖动(防雪崩式集体重连)。

图 7时间轴上的心跳 · 按一下"对面拔网线"
绿点=心跳往返 · 红=空等 · 虚线=重连

拔线版:客户端 60s 心跳石沉大海→readerIdle 超时→主动断开重连;服务端 90s(3×30)不见任何包→关闭回收。没有心跳,这半开连接要等 TCP keepalive 默认 2 小时——或者等它把连接池撑爆。

第 九 讲

快感的来源:参数背后都是设计

Netty 的"快"不是一个开关,是一串设计对位:epoll 边沿 + native transport(省 Java 中转数组)、EventLoop 数=核数×2 封顶(连接哈希绑定,扩不加锁)、池化 Direct 内存(arena 三级分配,回收 O(1))、无锁串行化(一个 Channel 一个线程)、FastThreadLocal(数组索引替代 hash)、ByteBuf 双指针/Composite(少拷贝少 flip)、ioRatio(IO 与任务的公平配额)、水位反压(isWritable+高低水位线保护慢消费者)。几个常调参数:

SO_BACKLOG accept 队列(1024 起,压测看 SYN 溢出)
TCP_NODELAY=true 关 Nagle——低延迟 RPC 必开,攒批场景才关
ALLOCATOR=UnpooledNoDirect 堆外出问题/调试场景的退路;生产默认 Pooled+Direct
WRITE_BUFFER_WATER_MARK 出站高/低水位:配 isWritable 做反压,快生产者别淹死慢消费者
ioRatio=55 IO 任务时间占比下限——大任务场景调低,别饿死报文
leakDetection.level 上线 DISABLED/采样,排雷期 PARANOID
要点追问"Netty 为什么比原生 NIO 好用"——别只答 API 友好:Selector 空轮询 bug 的规避(重建)、断连半包的开箱解码器、内存与线程模型的所有权清晰、以及十年生产事故喂出来的默认值。
