第 一 讲

IoC:把"造对象"的权力上交

没有 Spring 的世界,OrderController 要自己 new OrderService,OrderService 再自己 new Mapper、new DataSource……依赖关系散落在代码里,对象之间焊死:换实现要改源码、测一个方法要先养一池子真对象、单例只能人手一份管。Spring 的思路是反过来:你只声明"我需要什么"(构造器参数/@Autowired 字段),怎么造、何时造、造几个、给谁用,全交给容器——这就是控制反转(IoC);容器把造好的对象"喂"进来,即依赖注入(DI)。

BeanFactory 是地基(延迟初始化、只认依赖),ApplicationContext 在其上加了资源加载、事件广播、国际化、Environment、且默认预实例化全部单例——实际开发你面对的永远是后者。"IoC 只是换了个 new 的地方"这句吐槽,漏掉的重点是:创建权收归容器之后,生命周期管理、代理增强、依赖调度这些横切能力才有插手的机会——后面十一讲全从这里长出来。

图 1两条路:自己 new vs 交给容器,再写个单测试试

左列的"焊点"每一处都锁死了实现类型,换 Mock 得动源码;右列声明与装配分离,测试容器把 MockBean 塞进单例池就完事——这就是"DIP(依赖倒置)的工程落地"。

第 二 讲

Bean 生命周期:一个对象的十五站打卡

Bean 从"类"变成"池里的单例"要过一长串关卡,而每个关卡都是 Spring 生态的插座:实例化(反射调构造器)→ 属性填充(@Autowired 在这里被 AutowiredAnnotationBPP 处理)→ Aware 三连(beanName/BeanFactory/ApplicationContext 送"身份证")→ BPP 前置 → @PostConstruct → afterPropertiesSet → init-method → BPP 后置(★代理常在此诞生) → 进单例池服役 → 容器关闭时 @PreDestroy → destroy。

两个高频追问先答了:@PostConstruct 早于 InitializingBean,后者早于 init-method(注解→接口→配置,侵入度递增);@Transactional/@Async 的代理是在 BPP 后置做的——所以它们拿到的方法拦截,发生在你的 init-method 之后:init-method 里调自己带事务的方法,"事务"还不存在(第 5 讲的前奏)。

图 2生命周期打卡台 · 逐站盖章,看每站的"插座"都谁在用

点左侧任意一站可直接跳转。特别留意 ③④⑤ Aware(自己拿容器)、⑩ BPP 后置——"代理诞生"那一站,第 4、5 讲的演员就是从这儿登场的。

要点Bean 生命周期一句话背诵版:实例化 → 属性注入 → Aware → BPP前 → 三个 init → BPP后(代理) → 使用 → 两个 destroy。谁能插进来改 Bean:BPP;谁能改"图纸"(BeanDefinition):BFPP 家族——第 10 讲系统盘点。

第 三 讲

循环依赖:A 等 B、B 等 A,三级缓存怎么解的

ServiceA 注入了 ServiceB,ServiceB 又注入 ServiceA——构造互相依赖时死锁无解,但字段/setter 注入有救,因为"实例化"和"属性填充"是两步:A 构造完(哪怕属性全空)就能先曝光一个早期引用给 B 用。三级缓存各司其职:L1 成品池 / L2 半成品池(存曝光出来的早期引用)/ L3 工厂池(存 ObjectFactory,延迟决定"给你裸对象还是代理")。

为什么非要三级而不是两级?——如果 A 需要代理,必须保证所有人拿到的都是同一个代理。裸对象一旦先发出去就不能再"追认"成代理;L3 存工厂,正是为了在"真有人来要早期引用"的那一刻才执行 getEarlyBeanReference(提前走一遍 BPP 的代理化),然后把结果落进 L2 复用。构造器注入为什么救不了:A 连"实例化"都没完成,工厂也无从谈起——直接 BeanCurrentlyInCreationException。@Lazy 能解:先塞一个"用到才找"的占位代理。

图 3三级缓存棋盘 · 三种注入姿势,三种命运
注入姿势:
A=绿 B=青 · 橙描边 = 已被 BPP 提前代理化 · L3 里的 chip 是"工厂"不是对象

字段版走完八步;切"构造器注入"再连播——第 3 步当场爆红。Boot 2.6 起循环依赖默认直接报错(spring.main.allow-circular-references=false),官方态度:三级缓存是补丁不是设计,该拆环拆环。

想一想:为什么"原型(prototype)bean 的相互依赖"三级缓存也救不了?——L2/L3 存的早期引用,原型根本不留任何缓存,谁也没法"回头给你"——容器只能如实报 BeanCurrentlyInCreationException。

第 四 讲

AOP:给你的方法穿一层"拦截马甲"

AOP 把"每个方法都要做但和业务无关"的事(开事务、打日志、鉴权、埋点)抽成切面,在方法调用前后织入。Spring 的实现不是改字节码织入,而是"造一个替身对象":容器里放进单例池的根本不是你的 OrderService,而是它的代理;调用方拿到的引用就是代理,代理先跑通知(advice),再决定调不调真身。

两套分身术:JDK 动态代理——目标实现了接口,代理类 implements 同一批接口(所以(OrderApi)bean 能转,但 (OrderServiceImpl)bean 会 ClassCastException,经典事故);CGLIB——没接口就生成目标类的子类覆写方法(final 类/final 方法因此无法代理)。Spring Boot 默认全用 CGLIB(proxyTargetClass=true),统一行为少踩坑。

第 五 讲

代理的禁区:这四种调用绕过马甲

理解了"容器给的是替身",事故就都能预判:代理只在"从外面进来"的调用生效。① 自调用——a() 里调 b(),走的是 this(真身),不经过替身,b() 上的 @Transactional 形同虚设;② new OrderService() 自己 new 的,根本没有容器参与,裸得彻底;③ 方法/类是 private、static、final 的——JDK 代理只认接口方法,CGLIB 子类覆写不到 final/private(跨类可见性都不给);④ 类压根没被组件扫描(漏了 @Service / 包不在扫描路径)——容器里没有它的 Bean。

自调用的解法按优雅度排序:把 b() 拆到另一个 Bean(最正);注入自己的代理再调(@Autowired OrderService self);((OrderService)AopContext.currentProxy()).b()(需 exposeProxy=true);或干脆用 AspectJ 编译期织入(不再是"替身"而是"换心")。

图 5一个绿点子的两世为人 · 走代理 vs 走 this
代理替身(容器里存的是它)
@Service
class OrderService {
  @Transactional(READ_COMMITTED) public void a() {
     this.b();   // ← 事故现场
  }
  @Transactional public void b() { insertLog(); }
}
点右侧剧本开演。

剧本一:外部调 a() → a() 里 this.b()——绿点子绕过虚线墙直落真身,事务通知没被触发(单测里"数据没回滚"多半就是它)。右侧禁区 chips 逐条点,每条都是一个真实工单。

第 六 讲

注解背后是谁:Spring 没有魔法,只有扫描器和处理器

Java 注解本身零行为,行为全在那个"读注解的人"身上。这张牌墙每张牌正面是你天天写的注解,背面:谁处理、什么时机处理。把它翻完,你对 Spring 的理解就从"配置玄学"升级为"对象生命周期上的处理器网络"——这也是所有自研 starter、@Enable 全家桶的底层语法。

图 6注解翻牌墙 · 点任何一张,看它背后的打工人

注意三张"细思恐极"牌:@Configuration 的类会被 ConfigurationClassPostProcessor 用 CGLIB 再包一层——@Bean 方法互相调用拿到的仍是单例(普通类那样调就是 new 两个);@Autowired 找 notQualified 的候选按类型;@Value 的 ${...} 靠 PropertySourcesPlaceholderConfigurer 在 BFPP 阶段替换。

第 七 讲

事务凭什么跨方法生效:一条和线程绑死的连接

@Transactional 没有把 Connection 传参传到各层——它干了件更巧的事:开启事务时从连接池借一条连接,塞进 ThreadLocal(TransactionSynchronizationManager 的 map:{dataSource → ConnectionHolder})。之后同一线程上无论套多少层 Service、Mapper,MyBatis/JdbcTemplate 拿连接时先查这本"线程账",查到活跃 Holder 就用同一条连接、同一个事务;查不到才新借一条自动提交的。

所以——事务失效的第 N 个隐藏原因:方法里开新线程跑 SQL,新线程的 ThreadLocal 是空的,拿的是另一条连接,主事务回滚管不着它(提交也是)。另一面:传播 REQUIRED"加入"的实质就是"复用这条线程绑定连接";REQUIRES_NEW"挂起"的实质是把旧 Holder 从 ThreadLocal 解绑暂存,借新连接绑上,完事再换回来。下一讲用动画拆这两种传播。

http-nio-8080-exec-1 的调用栈

{ }
借还计数:借 0 次 · 用 0 次 SQL

没事务:每句 SQL 借一次还一次(3 借 3 还,各自独立提交);有事务:开头借一次绑进 ThreadLocal,三句全走它,commit 后才还——"一个连接管到底"就是 Spring 事务的实体。

第 八 讲

七种传播行为:就记三个主角 + 一条总则

传播行为回答的问题只有一个:inner 方法被 outer 方法调用时,"我的事务"怎么算。总则:有(当前)事务就"用/参合",没有就"造/不造、允许不允许"。REQUIRED(默认):有则加入、无则新建——内外一条命,一起提交一起回滚;REQUIRES_NEW:无论如何新开一个,外层连接被挂起——inner 的生死与 outer 无关;NESTED:有则用同一连接打 savepoint,inner 回滚只回滚到锚点、outer 可继续;没则等价 REQUIRED。剩下的:MANDATORY(必须有,不然 IllegalTransactionStateException)/ NEVER(必须没有)/ NOT_SUPPORTED(有就挂起,清空 ThreadLocal 执行)/ SUPPORTS(随缘)——见名知义,考场外卡。

图 8双车道账本 · 外方法在上,内方法在下,颜色=各自的事务命运
outer T1
inner T2
inner 的传播:

绿 = 活跃事务,灰 = 挂起,橙 = 回滚销毁。REQUIRED 下 inner 抛异常被 catch 也不安全——共享事务已被标记 rollback-only,outer 提交时静默炸 UnexpectedRollbackException(经典血案,记住这条账)。REQUIRES_NEW 里 inner 回滚不影响 outer;NESTED 回滚到 savepoint,outer 继续。

第 九 讲

事务失效开关台:把死法都拨一遍

把"代理是否生效 × 异常是否够格触发回滚"两根主线做成开关台:任何一个组合都能拨出来看结局。回滚规则再强调一次默认口径:RuntimeException 和 Error 回滚,checked 异常不回滚(rollbackFor = Exception.class 可扩列,写事务注解建议直接标它);而"异常被 catch 吞掉"= 事务拦截器根本没看见异常,自然不滚——吞不吞异常,决定权在方法外的代理,不在你自己。

rollbackFor = Exception.class 已声明

b() 是 private 方法

前提:方法执行到中途抛了异常(类型看第一档)。三个结论位:代理在不在、拦截器看没看见异常、最终提没提交。全拨一遍,面试那道"事务失效场景"你就有肌肉记忆了。

第 十 讲

扩展点管线:框架把自己的缝留好了

Spring 的"可插件化"集中在这几道缝,按容器启动顺序站队:BeanDefinitionRegistryPostProcessor(还能注册定义——MyBatis 的 MapperScanner 就是在这站把每个 Mapper 接口注册成 Bean)、BeanFactoryPostProcessor(改现成定义 / 占位符替换,PropertySourcesPlaceholderConfigurer)、BeanPostProcessor(逐个 Bean 出厂前后加工——AOP 代理、Aware 调度、注解注入全在这层)、FactoryBean("造 Bean 的 Bean",getObject() 说了算,getBean("&xx") 拿本体)、ApplicationListener 与三个 *Event。再往上,@EnableXxx 的套路是:@Import 一个 Registrar 或配置类,把一套 Bean 塞进管线。

图 10管线站点图 · 点任意一站,看"谁来这儿办过事"

顺序记忆:先改"图纸"(定义级:注册→加工),后改"成品"(实例级:前后加工),最后"广播"(事件级)。写中间件/自研 starter 的功课,基本都落在这五站。

第 十一 讲

事件与异步:解耦不是 MQ 的专利

进程内事件总线:applicationEventPublisher.publishEvent(new OrderCreated(...)),订阅方 @EventListener。默认同步同线程——发布者按 @Order 挨个调用监听者,异常会传回去(别指望它天然解耦事务)。要异步:@EnableAsync + 监听者标 @Async(扔给线程池,发布即返回)。而真正的大杀器是 @TransactionalEventListener(phase = AFTER_COMMIT):业务事务提交成功我才执行,回滚了我根本不出场——"下单成功后发短信/发积分"这类副作用的正解,免得在业务事务里同步调三方接口,拖长事务还制造"钱扣了短信没发"的不一致。

边界也要说清:进程内事件不持久、不重试、不跨进程,单机解耦够用;要可靠投递,那是 MQ + 本地消息表/事务消息的活。

图 11一颗事件的旅行 · 线程颜色 = 谁在跑
main 线程(exec-1)
task-exec 线程池
绿 = main 线程执行 · 紫 = 线程池异步 · 青 = 提交后才醒

两个剧本只差一件事:提交 or 回滚。AFTER_COMMIT 监听者在回滚剧本里全程没亮过——副作用与主事务的生死约定,就靠这一个注解,不需要把业务代码搅成一锅。

第 十二 讲

Spring MVC:DispatcherServlet 的九步工作流

一个 GET /order/7 的全部历程:请求打到前端控制器 DispatcherServlet → ① HandlerMapping 按 URL+method 匹配到 @GetMapping 方法(带回拦截器链);② HandlerAdapter 适配调用(解耦"怎么调"与"调谁");③ 拦截器 preHandle(返回 false 一路短路,连 Controller 都不进);④ 参数解析器把 HTTP 世界翻译成方法入参(@PathVariable、@RequestBody 走 HttpMessageConverter 反序列化);⑤ 反射调用 Controller;⑥ 返回值处理:@ResponseBody 再走 MessageConverter 序列化 JSON;⑦ postHandle → ⑧ 视图解析(REST 场景跳过)→ ⑨ afterCompletion(清尾,资源释放)。写过的每个 @RestController 都在这条流水线上。

图 12九步流水线 · 顺手拨一下"拦截器否决"开关

否决版在第 ③ 步提前散场——但 afterCompletion 依然会为"已经跑过的拦截器"执行(倒序),这是它做清理(比如登录态 ThreadLocal remove)的原因。

要点追问"Filter、Interceptor、AOP 谁先谁后?"——Filter(Servlet 规范,容器管) → DispatcherServlet → Interceptor(Spring MVC 管) → AOP(Bean 代理层管)。粒度越往里越懂"业务方法",越往外越懂"原始请求"。
