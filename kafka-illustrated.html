Kafka
图解讲义

先立规矩:topic 只是逻辑名,分区(partition)才是并行与有序的单位。往三个分区发十条带 key 的消息——看路由、看堆积,顺带理解"顺序到底是在哪一层被保证的"。

序分区账本 · hash(key) 决定去哪个抽屉
同一 key 永远进同一分区,分区内 FIFO——这是 Kafka 给"顺序"的全部承诺。

"扩分区"一下:hash%4 让后续 key=42 换了抽屉,同一订单的新消息和旧消息分家,顺序当场破产——分区数要按终局容量一次定够,或按业务键做自定义 partitioner 兜底。

第 一 讲

它不是队列,是一份可复制的提交日志

传统 MQ(RabbitMQ 式):消息消费即删除,队列是工作清单。Kafka 反过来:消息追加进不可变的分区日志,消费只是"带着 offset 来读",读完不删,过期才按时间/大小清理。这一字之差带来三个超能力:重放(新消费组从 0 号位开始把历史读一遍)、解耦的速度差(消费者按自己的节奏,日志替它扛住尖峰)、横向扩展(按分区拆并行度,加机器加分区)。代价:消息不是"事件到达信号",是"事实记录"——用它当传统低延迟小队列的,多半用错了。

骨架:producer/broker集群(topic→partitions,每分区多副本)/consumer group;ZooKeeper 管旧世界(集群元数据+控制器选举),KRaft 模式(3.x 起 GA)把元数据搬进内核——元数据本身也不过是一份日志,理念自洽。Consumer 端不 push 只 pull:消费节奏消费者自定、拉批摊薄开销、背压天然形成——代价是要自己处理"没消息时别空转"(长轮询)。

第 二 讲

副本、LEO 与 HW:水位线才是真相

每个分区一 Leader 若干 Follower,生产者只写 Leader,Follower 像消费者一样拉取(而非被推送)同步——角色可互换的实现优雅。两条水位:LEO(本副本已写到的末端)与 HW=ISR 全体 LEO 的最小值——"至少被 ISR 全部持有"才敢告诉消费者"你读到这就是已提交"。ISR 是"跟得上"的副本集合(lag 超 replica.lag.time.max.ms 踢出):ISR 缩到只剩 Leader,ack=all 实质退化成单点;全 Leader 挂且 ISR 空,面临电车难题——unclean 选举从非 ISR 拉一个(可能少几条=数据回退丢)或干脆不可用等新副本。min.insync.replicas=2 + acks=all 把"可用性与一致性"的选择题变成运行时的硬约束:副本没追齐就拒绝写。

图 1三副本的水位 · 生产、Follower 追齐、踢出 ISR、unclean 选举
蓝=已写 LEO,绿=可消费区(≤HW)。

断网剧本:2 号被踢出 ISR,HW 由剩下两个定——写入还能过(2 ISR ≥ min.insync=2);再杀 Leader,从 ISR 里的 Follower1 重选,数据完好。但若是"断网的那个被 unclean 扶正"——看它的水位比真相短一截,那几条已确认的消息从宇宙中消失。这就是 min.insync + acks=all + 不开 unclean 的三角誓言。

第 三 讲

消费组:分区是分配的最小单位

同组内一个分区至多被一个消费者领走(组内并行度=分区数,消费者多于分区=闲的);不同组互不影响(发布订阅的"订阅"就是组)。新成员进出触发 rebalance(CooperativeStickyAssignor 增量再分配,老 RangeAssignor 全员 stop-the-world):期间全组暂停消费——rebalance 风暴是消费端的头号隐形杀手(消费太慢触发 max.poll.interval.ms 超时→被踢→再触发别人 rebalance→雪崩)。位移即身份:offset 提交(__consumer_offsets)决定"下次从哪读":自动提交=可能重复(处理未完位移先走),手动=可能丢(先提位移后处理);正解是处理完一批再同步提交,或干脆把业务幂等做硬,把"至少一次"当默认语义。

图 2四人抢三坑 · rebalance 与位移提交的两种事故

第 4 人上线:C 从"闲"变"接盘 partition2",A 交出——交接窗口内消息可能双读(at-least-once 的日常)。提交事故:自动提交那条"处理了但没记账"的消息,重启后被再消费一遍;反过来先提交再处理,崩溃即永久跳过。要么幂等,要么手动+同步。

第 四 讲

为什么单集群能扛百万级 TPS

四板斧:① 顺序写盘——日志只 append,机械盘也能几十 MB/s 起,随机写的寻道地狱直接绕过(分区再多也救不了随机写,但 Kafka 反正用顺序写把随机性丢给消费端);② page cache——不自己搞缓存,读写都走 OS 页缓存,进程重启缓存还在,零成本换页;③ 零拷贝 sendfile——消费批量拉取,数据 磁盘→页缓存→网卡,不进用户态(上一本的图 5 第二式);④ 批量与压缩——生产端 linger+batch 攒够才发,整批 lz4/zstd 压,一次网络往返摊薄一切。

图 3写一百万条:随机小写 vs 顺序追加 vs 带攒批

数字是夸张的比例示意,方向真实:顺序写≈内存写量级,随机小写慢两个数量级;攒批再把"每消息一请求"的固定开销除以一万。Kafka 快不是黑魔法,是把机械盘时代"写"的每一条物理定律都用对了方向。

第 五 讲

有序性与幂等生产者

"Kafka 保证顺序"的完整句是:单分区内、单生产者Session内有序。两个反例天天发生:① 没有 key(或 key 太散)→ 同一订单的创建/支付/发货被分到三个分区,三个消费者并发赛跑;② 老式重试+无幂等:网络抖动 broker 其实落了但没回 ack → 重试重复写入。解药是 enable.idempotence=true:broker 给每个 Producer ID 记每分区的 seq 号,重复/乱序的批次直接丢弃(只保证单 session——重启换 pid 的重复仍要靠业务幂等);再把 max.in.flight.requests≤5 钉住,顺序性也顺带不破。

图 4一条重试的旅程 · 幂等开与关,日志长两样

broker 视角的两次"同一条消息"字节完全相同,唯一能分辨的是幂等模式下附带的 pid+seq。第三幕解释那条著名参数的因果:多批次在途 + 只丢中间批 → 后批先到,分区内顺序就破了——所以幂等模式限 in.flight≤5(顺序与吞吐的数学交点)。

第 六 讲

参数生死局:不丢、不重、可用,选几个?

消息的命运由三端各一把闸决定:生产端 acks(0=发完就走 / 1=Leader 落盘 / all=ISR 齐)、broker 端 min.insync.replicas(all 生效的门槛)+ 副本机制、消费端提交时机。"不丢"的套餐:acks=all + min.insync=2 + replicas≥3 + 不开 unclean + 手动提交后置;此时 ISR 缩到 1 会拒写(NotEnoughReplicas)——用可用性换持久性。"不重"没有银弹:网络世界里"已送达"和"已确认"天然可以错身,at-least-once + 消费幂等(唯一键去重)才是工程稳态;"exactly-once"是事务 API 在Kafka 体系内的自嗨,跨到 MySQL 就破功(上一本的分布式锁边界感,这里一模一样)。

图 5丢包矩阵 · 三种灾难 × 三种配置,红格=丢消息
行=故障剧本,列=参数套餐。先想清楚业务能容忍哪种错。
要点面试终极题"Kafka 如何保证不丢消息"三段论背下来:生产端(acks=all + 重试带幂等 + 送失败的本地兜底)、broker 端(rep≥3 + min.insync=2 + acks=all 三者锁死 + 关 unclean)、消费端(处理完再提交+ 死信兜底)——少一段都不算答完。

第 七 讲

积压:Kafka 的痛点和它的解药是同一件事

Lag=最新 offset − 消费组 offset:积压本身不可怕(日志就是为扛尖峰而生),可怕的是"有增无减"和"涨跌与告警同频"的慢性病。定位链:先看单分区 vs 全分区(单分区积压=热点 key,加分区无用,要改 key 或二次分发);再看消费端曲线形态(锯齿=某任务周期性拖慢;平直爬升=纯吞吐不足)。扩消费的天花板是分区数——>分区不够:先拆"拉取-处理-提交"三段,把处理丢线程池按 key 保序地并行(伪分区),或消费端二次队列分流;顺手把重试从"睡眠阻塞"改成"退避重投"(一次毒丸消息 sleep 60s,整个分区 lag 起飞)。治理完记得看生产端有没有跟着降速失败——队列是守恒的,压力只会搬家。

图 6Lag 曲线诊室 · 四种病形,四种处方

四条曲线的形状学:"齐涨"看总并行,"一柱独高"看 key,"锯齿"看重试与慢依赖,"方波"看会话超时与 GC 抖动——先辨形,再开方,和心电图一个道理。

第 八 讲

Log Compaction:让日志变成一张表

普通保留策略按时间/大小截断——适合事件流;但"状态"类 topic(用户资料变更、商品快照、Kafka 自己的 __consumer_offsets)要的是"每个 key 的当前值永远可重放"。开启 cleanup.policy=compact:后台线程不断做一件事——同一 key 只保留最新一条(+墓碑用于删除),老记录被逻辑清走,日志永远完整又不会无限膨胀。消费方从 0 读一遍=拿到全量快照(状态),继续追新消息=增量事件——"全量+增量"一套协议,这就是 Kafka 能当轻量数据库/注册中心、Flink 拿它做 checkpoint 存储底座的秘密。

注意它不保序不保历史(中间的 v2 没了),所以只配状态不配审计;事件溯源要完整历史,用普通保留或双 topic 分工。

第 九 讲

事务与 "exactly-once" 的边界

Kafka 事务解决的是一类特定问题:消费-处理-生产(读-转-写)这条链路的原子性(流处理 ETL 的本质)。事务生产者 initTransactions→begin→produce(可跨 topic/分区)→sendOffsetsToTransaction(把消费位移也写进同一事务)→commit;broker 端由 transaction coordinator + __transaction_state 日志记账(两阶段提交!上一本的影子又现)。消费端 isolation=read_committed 只看到已提交事务的消息——依据是 LSO(最后一条稳定偏移,= 所有在途事务的最小 first offset 前一位),未定事务对读者是一片灰。

边界要讲透:eos 只在 Kafka→Kafka 的世界闭环。消费端把消息写进 MySQL 再 commit offset?MySQL 不在事务协调器里——崩溃时机不同要么重要么丢。跨系统的"精确一次"永远是:at-least-once + 业务幂等(唯一键/去重表/版本比较),Kafka 事务帮你把"体系内"的那段磨平,体系外的那段,还是分布式系统那课的内容。

图 8read_committed 的眼里,日志分三段 · 提交/中止各演一次

未定事务=灰色不可见区,LSO 卡在它们前面;commit 落子转绿,abort 变红叉(标记还在,读时跳过,靠日志清理收尸)。"消费方看不见"和"没发生过"是两回事——事务隔离的这句话,放到任何数据库都成立。
