第 一 讲

并发三大病害:原子性、可见性、有序性

i++ 看着是一行,机器里是三步:读内存 → 加一 → 写回。两个线程交错执行,两条"读"可能读到同一个旧值——写回两次,只加了一次。这是原子性问题;线程各自抱着 CPU 缓存/工作内存的副本,改了别人看不见,是可见性问题;编译器和 CPU 为了快,会悄悄调换不冲突的指令,是有序性问题。三者叠加,才有 JMM 和 java.util.concurrent 这一整套解药。

i 的初值 = 5。先"裸奔"跑一局,再上 synchronized 跑一局,对比结果。

裸奔局里留意"读→加→写"被打断的瞬间——两次读拿到同一个 5,就注定少加一次。真实程序里这个竞争窗口每天在产线上演,只是概率稀释成了"偶尔少一单"。

要点一句话分清:原子性解决"做一半被人插队"(锁/CAS),可见性解决"我改了你不知道"(volatile/锁),有序性解决"先后被偷偷调换"(屏障/依赖约束)。后三讲各治一味。

第 二 讲

JMM:happens-before 是法官,不是时钟

Java 内存模型(JMM)不描述缓存硬件,它是一份契约:规定"什么情况下,线程 A 的写保证对线程 B 可见"。判据叫 happens-before——别读成"时间上先发生",它是可见性秩序的偏序关系。八条常用规则:程序顺序、监视器锁(解锁 hb 后续加锁)、volatile 写 hb 后续读、线程 start/run、join 收尾、传递性……两个操作若没有 happens-before 关系,JVM 有权任意重排、不保证可见。

图 2Dekker 小剧场 · 加不加屏障,两种世界
线程 A
1. x = 1
2. r1 = y.read()
线程 B
1. y = 1
2. r2 = x.read()
x、y 初值 0。问:r1 == 0 且 r2 == 0 可能发生吗?

无同步时,可能!A 的两行被重排成"先读 y 再写 x",B 同样——两人各读到对方的 0。这不是 bug 而是契约允许:两条语句无数据依赖,JMM 不管。写 x 用 volatile(或加锁)后,"写 hb 读"链子锁死,同局面不可能再出现。

第 三 讲

volatile:可见性 + 有序性,唯独不给原子性

volatile 的硬件落地:写时刷主存 + 失效其他 CPU 缓存行(锁前缀指令),读时直读;同时读写两侧插内存屏障,配合 JMM 规则杜绝绕过它的重排。适用画像就两种:状态位标志(一写多读)和 DCL 单例的引用。为什么 DCL 必须 volatile?instance = new Singleton() 实为三步:分配内存→初始化→指派针;后两步重排时,第二个线程在第一线程"还没构造完"的对象上判空通过,拿到半成品。它给不了原子性——volatile i++ 照样丢更新。

口诀:一写多读用 volatile,多写用锁或原子类。追问"volatile 怎么保证有序"别背硬件细节,答 JMM 规则:volatile 写 hb 后面对它的读,且它与前后语句间不许跨越重排(屏障实现这一契约)。

第 四 讲

synchronized 锁升级:从无锁一路到重量级

HotSpot 的发现:大多数加锁其实根本没竞争,不该一上来就惊动操作系统。于是锁在对象头 Mark Word 里逐级"变身":无锁 → 偏向锁(记录归属线程,同一把钥匙只用一个人——进出自如零开销,但 15 后交替竞争要撤销,反而更亏,JDK 15 默认废弃)→ 轻量级锁(CAS 把 Mark Word 拷进线程栈的 Lock Record,自旋等待,不停用户态)→ 重量级锁(CAS 几次仍失败,膨胀出 Monitor 对象,没抢到的 park 挂起,交给 OS 调度——用户/内核态切换的贵钱)。锁只能升不能降(回收例外)。

Monitor 内部三件套:owner(持锁人)、EntryList(等锁队列)、WaitSet(wait 后睡觉的池子)——wait/notify 就是把线程在前两者间搬运。升级不可逆:高频交替访问会反复撤销偏向,这正是 15 之后干脆默认关掉偏向锁的原因。

第 五 讲

CAS:乐观的代价、ABA 与 LongAdder

"我以为它是 5,还是 5 我就改成 6,不是 5 我重来"——这就是 CAS(比较并交换),一条 CPU 原子指令(cmpxchg)。Atomic* 家族、synchronized 的轻量级锁、ConcurrentHashMap 的空桶写入,底下全是它。三大代价:高竞争=高自旋(三个线程九个循环轮着白干 CPU);只盯一个位置(多变量原子还得回到锁);ABA 问题(值转一圈回来,中间被谁动过它不知道)。解药对应:竞争高换 LongAdder(热点拆 cell 数组分桶记账,读时 sum());需要版本语义用 AtomicStampedReference(值+版本号双保险)。

ABA 要命吗?纯计数不要命;链表节点复用/栈弹栈就致命(节点被回收又重用,指针校验被骗过)。LongAdder 的哲学:把"一个热门值"变"一串分片",写永不争抢,读再合并——用空间换冲突,和分段锁一脉相承。

第 六 讲

AQS:一个 int、一条队列、一套模板

ReentrantLock、CountDownLatch、Semaphore 看着各玩各的,骨架都是 AQS(AbstractQueuedSynchronizer):一个 volatile int state 表达资源状态(锁:0/1,重入次数;共享:信号量个数、倒数计数),加不上锁的线程包成节点挂进 CLH 双向队列,park 睡觉;释放时唤醒队头继续抢。子类只需重写 tryAcquire/tryRelease(独占)或 tryAcquireShared(共享)几个钩子——这就是"模板方法模式"在 JUC 里的封神之作。公平 vs 非公平差一行代码:加锁前先不先看队里有没有人等着(有=老实排队=公平;没有也抢=吞吐高但可能饿死后来者)。

第 七 讲

线程池下半场:拒绝策略与参数怎么定

开篇沙盘演了执行顺序,这讲补两个工程问题。队满了怎么办——四种内置拒绝策略:AbortPolicy(默认,抛异常,快而诚实)、CallerRunsPolicy(让提交者自己跑,天然反压,但会拖慢上游)、DiscardPolicy(静默丢,业务别用)、DiscardOldestPolicy(丢最老的腾位,适合时效性数据如行情)。线程数怎么定——先脑公式:CPU 密集 N+1、IO 密集理论 2N,但真实答案永远是压测:从核数起步,盯三个指标调(队列堆积、CPU 利用率、任务 P99)。IO 密集远超 2N 也常见(取决于下游,不取决于本机核数)。

CallerRuns 的妙处是不需要任何协调就实现反压:提交方被拉去干活,自然就慢下来了。调音台里把线程从 1 加到 64,看三个指标怎么此消彼长——最优值只存在于你的流量模型里,不存在于博客口诀里。

第 八 讲

ThreadLocal:每个线程一个抽屉,以及忘记锁门

ThreadLocal 不是"变量本地化"的魔法:每个 Thread 对象自带一张 ThreadLocalMap,key 是 ThreadLocal 的弱引用,value 是值本体。get/set 都是"以当前 TL 实例为 key 查自己的表"——不同线程天然隔离,免锁。名场面三连:SimpleDateFormat 线程隔离(历史)、用户上下文/traceId 透传、Spring 事务的 Connection 绑定(和 MySQL 册的 ThreadLocal 账本同一个思想)。泄漏点:线程池的线程不死,弱引用 key 被 GC 回收后,value 还挂在表里变"僵尸";下次 set 会顺带清理,但最可靠永远是——用完 finally remove()。

第 九 讲

ConcurrentHashMap:从分段锁到"一桶一锁"

JDK 7 的 Segment(默认 16 段)把并发粒度定死在"段";JDK 8 推倒重来:空桶用 CAS 写入,非空桶对头节点 synchronized——锁粒度细化到单个桶,并发度=数组长度且能扩容。配套的细活:链表长度 ≥8 且数组 ≥64 才树化(否则先扩容);扩容用 sizeCtl + ForwardingNode 做多线程协作迁移(帮忙搬桶的线程随处可见);计数不用 AtomicLong 硬攒,用 CounterCells(还是 LongAdder 那招)。

图 916 桶棋盘 · put 时到底锁了什么

绿色=CAS 直写空桶;黄色=synchronized 锁住该桶头节点(别的桶照常营业);红色=这桶太挤转红黑树。对比 1.7:两个 key 落不同段才并行——8 的桶粒度把"分段锁"的思想做到了极致。

第 十 讲

三剑客:Latch 等事件、Barrier 等同伴、Semaphore 限流量

三个都是 AQS 共享模式的皮:CountDownLatch=一次性倒计时门闩(N 件事都做完我才走;N 个微服务健康检查后放行流量);CyclicBarrier=多人集合点(凑齐 N 个互相等,可重复用,还能在破局时跑一段 barrierAction——分片并行计算的"每轮对齐");Semaphore=令牌池(许可 N 个,acquire/release 控制并发访问量——限流、连接池、10 车道收费站)。一句话分工:Latch 是"别人等我",Barrier 是"我们等我们",Semaphore 是"人多请取号"。

图 10三扇门 · 每扇推一遍

看 Barrier 和 Latch 的关键区别:第二轮场景——Latch 归零即废;Barrier 放行后自动复位再来一局。Semaphore 演示 6 个任务抢 2 个许可,进出有序。

第 十一 讲

CompletableFuture:把回调拼成 DAG

Future 的痛:只能 get 干等、不能组合。CompletableFuture 把异步任务当积木:supplyAsync 起一枪,thenApply 串行变形,thenCombine 两路汇合,allOf 多路齐发,exceptionally/handle 兜异常,orTimeout(9+) 限时止损。两条铁律:① 不带 Async 后缀的回调"谁完成谁执行"(可能在你的主线程!),跨阶段续写要么统一带 Async+自定义 executor,要么接受在默认池;② 别用公共 ForkJoinPool 跑阻塞 IO——它按核数规划工人,一卡全卡,自建业务池才是正解。

图 11价格+库存并行查询的编排图 · 一颗令牌的旅程

两个供给节点并行起跑(默认池),都到货才点亮 combine——比串行快了近一半;超时分支里红色令牌半路坠毁,橙色兜底值顶上——主流程永不抛穿,这正是"异常也是一种数据流"的设计。

要点面试收口:并行编排省的是等待时间(max(a,b) 而非 a+b);executor 必须按 IO/CPU 分池;orTimeout 只"按时放弃",不真正中断底层 IO——连接照样占着,超时值还要配到 HTTP 客户端层。
