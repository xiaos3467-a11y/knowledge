先记住总纲:微服务=分布式系统的工程学费——服务发现、超时重试、配置下发、链路追踪、数据一致性,每样都是单体时代"免费"如今"付费"的能力。阵型摆齐,才谈得上打这场仗。

第 一 讲

什么时候该拆:先问发布痛不痛

拆分的合法理由只有两个:组织规模(一个模块的改动要排队等别人发版、代码权限难隔离)与差异化扩缩(报表服务要 16C,秒杀要弹性百台)。危险信号清单:改一处全量回归 2 小时、一次故障拖垮全站、团队 >20 人共仓。但别反向迷信——"微服务架构的单体"是全球大厂的主流形态:拆分服务数量应与团队人数同数量级(两个披萨原则),否则你得到的不是独立部署,而是分布式泥潭:本地方法调用变 RPC、事务变 saga、调试变链路考古。路线建议:模块化单体先行(Spring Modulith/包边界+ArchUnit 守门),痛到再拆,且从"接缝最清晰"的模块开刀——第 11 讲拆分方法论。

第 二 讲

注册中心:实例名单的生死簿

服务实例是动态的(扩缩/发布/宕机),调用方凭什么找到它?注册中心=服务名→实例列表的活账本:实例启动时注册+周期心跳续约,下线主动注销;注册中心按健康协议把超时未续的标记不健康乃至摘除。两套血统:Eureka(AP:自我保活,客户端每 30s 拉全量,极端时把死实例留着"反正比空列表强")、Nacos/Consul/ZK 系(偏 CP 或可配置,主动健康检查、支持推模式)。Spring Cloud 侧:DiscoveryClient 抽象统一,服务名变成 URI 的一部分——http://order-svc/api/x,由 LoadBalancer 把名字翻成真实实例。

图 1一条实例的生命线 · 注册→心跳→失联→摘除
时间轴=10s。心跳每 1s,失联 3s 标不健康、5s 摘除(参数为演示压缩,Eureka 默认 30/90s)。

猝死剧本里,"摘除延迟"就是错误窗口:名单还认为它在,打到它的调用会失败——所以调用侧的负载均衡要有"实例熔断"(连续失败临时摘)兜最后一段。两种剧本的对比也是"优雅下线为什么值得做"(K8s 册 preStop 的孪生兄弟)。

第 三 讲

OpenFeign 与负载均衡:声明式调用的魔法与算账

接口上写 @FeignClient("order-svc")+注解路由,调用方像本地方法一样用它——Feign=动态代理(第 14 册英雄)+ 服务发现 + LoadBalancer 的三合一套件:代理把方法翻译成 HTTP 请求,目标地址从注册中心实例表按负载均衡算法选。算法四件套值得实机感受:轮询(公平但无视快慢)、随机+权重、least-active(挑当前在途请求最少的实例)——慢实例被自动少投,异构集群友好。超时预算是这条链的生死线:Feign 的 connectTimeout/readTimeout 必须小于上游给你留的时间,否则上游已超时返回,你还在等下游——重试要配退避,且默认只重试幂等。

图 2100 次调用各算法落到谁 · 注意有一台是慢实例

四台实例,3 号天生慢。轮询把 1/4 流量继续喂给慢者(雪崩的温床);least-active 看见 3 号在途请求堆积,自动绕开——负载均衡的"智能"不在于匀,而在于感知谁不配。

第 四 讲

网关:城门官的三件事与灰度分流

Spring Cloud Gateway 的世界观=Route + Predicate + Filter:按断言(URL/Header/Cookie/权重)匹配路由,过过滤器链(鉴权、改写、限流、落日志)后转发。三件事守住城门:① 认证统一化(JWT 校验在网关做,业务只消费解析后的用户头);② 流控统一化(网关限总闸,Sentinel 在服务内做细粒度——两层别混);③ 流量染色与路由——灰度发布的实现底座:请求带用户标签/比例,网关按标签分流到 canary 版本池,新版本先吃 5% 真实流量,看错误率与 RT 再放量(配合注册中心元数据/双环境)。网关反模式:别在网关塞业务逻辑(它是城门不是大脑)、别让它成为没有水平扩展的单点。

第 五 讲

配置中心:改配置不再发版

三层坐标 namespace(环境) / group(业务) / dataId(文件) 把配置摆进 Nacos;应用启动时拉取,并落一份本地快照——注册中心挂了也能靠快照冷启动(这个设计请抄作业)。热更新链路:控制台发布 → 服务端推变更通知(长轮询挂起等变更)→ 客户端拉最新 → 刷新 Spring Environment → 发布 RefreshEvent → @RefreshScope 的 bean 销毁重建,下次调用拿到新值。三个坑:① @Value 的字段不会自动变,要刷的是 bean(所以配置类要 @RefreshScope,或干脆用 @ConfigurationProperties 重绑定);② 长连接池/线程池这类"重建很贵"的对象别挂 @RefreshScope;③ 改配置=改行为,和发版同级别的变更纪律(灰度推、审计、回滚)——配置中心把发布成本降到一次点击,也把事故成本降到一次手滑。

第 六 讲

重试风暴:每一次善意的重试,都在给火灾浇油

最温柔的雪崩:下游 RT 升高 → 上游超时重试 → 下游负载 ×2 → 更慢 → 更多层各自重试 → 乘法放大:A(重试3)→B(重试3)→C(重试3),C 收到的压力是 27 倍。三原则:① 只有一层重试(通常最靠近用户那一层,内部层快速失败);② 指数退避+抖动+重试预算(retry budget:10% 封顶,不是固定次数);③ 只重试幂等且值得的(GET/明确幂等键;POST 无幂等重试=重复下单)。配套认知:超时必须逐跳递减构成预算链——网关 3s、服务 2s、DAO 800ms,任何一层把时间用完,下层的成功都已无意义(第 3 册网关/第 10 册 Netty 的超时线在此汇合)。

图 5C 服务到底收到了多少请求?算给你看

朴素版:C 被打 27 倍流量,从"变慢"恶化成"彻底倒下"——它的死是上游的关心造成的。治理版:C 只收到 ≤2 倍,慢但活着;用户侧看到的是部分降级而非全站崩。这道乘法题,值得贴在每个服务网关的工位上。

第 七 讲

怎么拆:接缝在领域,数据跟服务走

拆分的北极星不是"服务数量",而是"一次业务动作尽量在一个服务内完成"——跨服务事务是失败设计。方法回到 DDD 语境:按限界上下文找"天然接缝"(订单/库存/营销各有各的模型语言),接缝处放 MQ(事件)而不是同步调用(命令链)。数据铁律:一个服务一个库,禁止跨库直连查表——别人的数据要,走它的 API 或它发的订阅;聚合查询用 CQRS(写归业务库、读归 ES/宽表,Canal 搬运——前两册的线头在这里汇齐)。拆完自检三问:改一个需求要动几个服务?某个库挂了会烧到谁?这条调用链有环吗(有的话,那个边界就是假的)。

第 八 讲(终)

韧性设计:假设一切都会坏

把这套阵型收拢成五问,架构评审直接照抄:① 任何依赖变慢 5 秒,我会怎样?(超时必须显式设,默认值都是赌博;逐跳预算递减)② 任何依赖彻底死,我会怎样?(熔断+降级路径:兜底值/静默跳过/明确拒绝——没有降级预案的熔断只是换个姿势报错)③ 我的重试会不会打死别人?(单层重试+退避+预算+幂等)④ 流量翻十倍,先垮哪个?(限流在网关粗、Sentinel 细、MQ 泄洪;弱点要压测点名)⑤ 出事了我 5 分钟内能定位吗?(traceId 全链贯穿、错误必带上下文、指标四金:延迟/流量/错误/饱和)。微服务的可靠性不在任何单点,在"故障传播的设计"——允许坏消息发生,阻断坏消息扩散。

要点毕业检查单一条:把第 15 讲的重试风暴、灰度、心跳、热更四个动画各重放一遍,能给别人讲清楚"为什么会这样"——讲得清,阵型就是你的了;讲不清,你还在使用说明书。
