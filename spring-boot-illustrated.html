        第 一 讲

        Boot 治的不是 Spring 的病,是"配置的病"

        Spring 本身把对象管理治好了,但"起一个新 Web 工程"仍是体力活:web.xml 或 JavaConfig、DispatcherServlet 手动注册、Tomcat 插件与部署描述符、Jackson 转换器手配、数据源和事务管理器一行行 bean、版本对不上还互相打架。Spring Boot 的答案:把"每个团队都要抄一遍的样板"沉淀成 starter + 自动配置 + 内嵌容器 + 可执行 jar——它不替换 Spring,它是 Spring 的"出厂预装配"。

        三个词记住 Boot:约定优于配置(默认值覆盖 90% 场景,如 H2 内存库自动配好连接串)、起步依赖(按"功能"聚合 jar 并统一版本)、自动配置(按 classpath 上有什么类,决定装不装某套 Bean——下一讲的漏斗)。它仍是 Spring:上一册的容器、生命周期、AOP、事务在这里 100% 成立。

        第 二 讲

        main 方法一行,背后十件事

        SpringApplication.run(App.class, args) 拆开:构造期——推断应用类型(SERVLET/REACTIVE/NONE)、从 SPI 加载 ApplicationContextInitializer 与 ApplicationListener、定位主配置类。运行期——广播 starting → 准备 Environment(命令行、profile、yml 全部汇入)→ 创建上下文 → refresh()(真正的重头:第 3 册整个生命周期在这里跑) → 调用 Runner 家族 → started/ready 事件。

        几个高频追问都藏在这十步里:内嵌 Tomcat 什么时候起?——refresh 中 InetServletWebServerApplicationContext.onRefresh 就起了(所以端口占用错在 Bean 创建之后、Runner 之前);CommandLineRunner/ApplicationRunner 何时跑?——容器就绪之后,预热、任务注册在这;失败呢?——FailureAnalyzers 链负责把 300 行堆栈翻译成人话(第 11 讲排障室)。

        图 2run() 十步流水 · 点任意一步看"谁在这埋了钩子"

        记住三个"钩子位":②的 Initializer(动手前改上下文)、⑤的 Environment(动手外加配置)、⑩的 Runner(动手完做业务)——绝大多数"启动时我要做点事"的需求都该落在其中之一,而不是散落在 @PostConstruct。

        第 三 讲

        自动装配漏斗:142 个候选怎么筛出你这 9 个

        @EnableAutoConfiguration → AutoConfigurationImportSelector → 读取 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports(Boot 3;2.x 在 spring.factories),拿到全部候选自动配置类 → 每个类头上都顶着一排 @Conditional:OnClass(类路径有 X 才装)、OnMissingBean(你没自己配我才配——这是"覆盖默认"的机制底座)、OnProperty、OnWebApplication……逐层过滤,最后进容器的只有十几到几十个。--debug/启动日志 ConditionEvaluationReport 就是这张漏斗的出厂检验单。

        理解到这一层,两个"玄学"当场破产:① 换连接池不用写配置——DataSourceAutoConfiguration 按顺序探测 Hikari→Tomcat→Dbcp,有 Hikari 类就装它(想换?引入对应类或自己定义 DataSource Bean,OnMissingBean 让位);② 排除自动配置:@SpringBootApplication(exclude=JpaRepositoriesAutoConfiguration.class)——嫌它自作主张时的标准撤回姿势。

        第 四 讲

        依赖仲裁与 BOM:谁压过了谁

        Maven 面对同一个库多版本入场的仲裁规则很朴素:最短路径优先,同深度先声明优先。坑由此而生:你 starter-web 里想要 spring-core 6.1,某个老工具包 depth-2 拽着 5.3 先声明了——老版本赢,Boot 全家桶被压,启动才炸 NoSuchMethodError。spring-boot-dependencies(BOM)是"家长令":它 import 一份 dependencyManagement,把所有传递依赖的版本钉死——你的 pom 继承 Boot parent 或 import BOM 后,无论依赖树里谁喊几版,家长说了算。

        实操三板斧:Boot parent 兜底(普通工程全走它,子模块引依赖不写 version);冲突显形靠 mvn dependency:tree -Dverbose 找"omitted for conflict";必须覆盖家长时,在 properties 里改版本变量(如 <jackson-bom.version>)而不是硬 import——后者会让"家长令"局部失效,迟早再打起来。

        图 4同一棵依赖树,BOM 前后两次仲裁
        没有 BOM(裸 Maven 仲裁)
        继承 spring-boot-starter-parent
        左边按 Maven 规则仲裁,右边"家长令"一票定版

        左:myutils 最短路径带着 spring-core:5.3 胜出——Boot 的 6.1 被 omitted,启动时方法签名对不上 NoSuchMethodError;右:BOM 钉 6.1,所有声明的"约等于"建议版本被统一抹平。这也是 Boot 升级时"别自作聪明钉版本"的由来。

        第 五 讲

        配置水塔:同一个 key,听上面的

        Boot 把配置源堆成一座水塔,同一 key 上层覆盖下层:命令行(>--server.port=9090) → SPRING_APPLICATION_JSON → 环境变量(SERVER_PORT) → 各 profile 的 application-{profile}.yml → 主 application.yml → @PropertySource → 默认值。profile 内部也分层:profile 文件压主文件,profile 顺序由 spring.profiles.group/active 定。

        配套心法:机密不进 yml——走环境变量/配置中心/加密的 ENC(...);@ConfigurationProperties 优于 @Value(批量绑定+宽松匹配+校验+IDE 元数据),@Value 留给单点;所谓宽松绑定:yml 里 my-app.name-server、环境变量 MY_APP_NAME_SERVER、System prop myAppNameServer——同一个键的三个变体,绑同一个字段。

        第 六 讲

        可执行 jar 解剖:为什么它不用 Tomcat 也能跑

        java -jar app.jar 跑起来的不是普通 jar。spring-boot-maven-plugin 打成 fat jar(jar in jar):META-INF/MANIFEST.MF 里 Main-Class 不是你的 App,而是 JarLauncher;Start-Class 才是你。MANIFEST 之下,你的类在 BOOT-INF/classes,100+ 个依赖 jar 原封不动嵌在 BOOT-INF/lib(不解压,靠自定义 LaunchedURLClassLoader 以嵌套路径直读);org/springframework/boot/loader 是这套启动魔术的实现。Tomcat 呢?tomcat-embed-core 就在 lib 里——它只是个库,ServletWebServerFactory 在代码里 new 出它并 listen 端口。

        这解释了三个现象:为什么 Boot 的 Main 类 IDE 能直接跑(类路径普通方式组装,没走 Launcher);为什么 fat jar 里资源要用 ClassLoader.getResource 而不是 File API(它在嵌套 jar 里,不是文件系统);为什么 java 9+ 的 -jar 仍可(Loader 只依赖标准 URLClassLoader 定制)。war 部署老 Tomcat 的兼容路径:继承 SpringBootServletInitializer 把"控制权"还给容器。

        第 七 讲

        Actuator:给运行中的进程装仪表盘

        spring-boot-starter-actuator 点亮一串 HTTP/JMX 端点:/health(健康检查聚合,探活/K8s 就绪探针直接吃它,management.endpoint.health.probes.enabled=true 出 liveness/readiness)、/metrics(Micrometer 指标,喂 Prometheus)、/info /env /configprops /beans /mappings /loggers(动态改日志级别!)、/heapdump /threaddump(现场拍片)、/shutdown。危险项(env 泄漏配置、heapdump 几百 M、shutdown 直接关服)必须收口:只暴露 health/info/metrics,挂 management.server.port 走内网,加 Spring Security。

        自定义三板斧:HealthIndicator 加一路依赖自检、@Bean Metric 埋业务指标、Micrometer Observation API 统一日志+指标+链路——Boot 3 把这三件事收进了"可观测性"一个门面。

        第 八 讲

        自研 Starter 工坊:把公司的轮子做成"引一下就能用"

        写一个 acme-sms-spring-boot-starter 只要四步(Boot 2.7/3 规范):① 两个约定模块——acme-sms-spring-boot-autoconfigure(装配逻辑)+ acme-sms-spring-boot-starter(空壳 pom 只聚合依赖,官方命名:第三方不要以 spring-boot 开头);② @ConfigurationProperties(prefix="acme.sms") 收配置;③ 自动配置类:候选 Bean + @ConditionalOnClass/@ConditionalOnMissingBean(用户自定义优先);④ 注册到 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports。完事——别的项目引 GAV、yml 配两行,@Autowired SmsService 即来。

        这套骨架和 Boot 官方 starter 完全同构——你现在回头看第 3 讲的漏斗,就能明白每一个官方自动配置类就是这么写的。工坊里五步走完,右侧同步"消费方视角"验收。

        图 8Starter 流水线 · 左边五步,右边消费方验收

        第 4 步那个"一行注册文件"是新手最常漏的——没有它,自动配置类只是个普通类,漏斗根本看不见它。Boot 2.x 对应写 spring.factories 的 EnableAutoConfiguration key,3.x 换 imports 文件(2.7 已双轨)。

        第 九 讲

        测试切片:别为一行 Controller 起整座城

        @SpringBootTest 把整个应用上下文拉起来——1200 个 Bean、真实数据源、内嵌 Tomcat,测一个 URL 路由要 40 秒;而且测试环境里那个"能启动"的假数据库还会污染结论。切片测试按层裁剪:@WebMvcTest 只装 web 层(Controller/Converter/Interceptor/Filter),Service 用 @MockitoBean(3.4+;旧 @MockBean)顶掉;@DataJpaTest 只装 JPA+数据源(默认换嵌入式库,且默认事务回滚不脏库);@JsonTest 只验序列化;要全链路再用 @SpringBootTest 点名几个场景。

        常见报错一步定位:@WebMvcTest 里 @Autowired Repository 报 NoSuchBean——切片压根不装它;把被测链路上的下游一律 Mock。CI 账本:切片 4s/类 vs 全量 40s/类,乘以 300 个测试文件就是每天多睡 3 小时。

        第 十 讲

        Boot 3 的门面换了什么

        3.x 四件大事:Jakarta EE 9+(javax.servlet→jakarta.*,所有依赖它的库都要重适配——升级卡半路多半卡在这)、Java 17 起步、可观测性统一(Micrometer Observation 一个 API 同时产指标+链路,Actuator Tracing 内置)、原生镜像 GraalVM(AOT 提前分析,启动毫秒级、内存砍半——代价是反射/代理要登记 reflect-config,框架"运行期魔法"受约束)。另外 2.7→3.0 迁移点:自动配置清单换 imports 文件、@MockBean→@MockitoBean、spring.factories 各 SPI 迁到 .imports/spring.子文件。

        AOT/native 对"老 Java 程序员"最扎心的推论:凡是运行期动态字节码(CGLIB、动态代理、Class.forName 配置加载)在 native 里都要提前登记——Spring 6 为此把大量运行期逻辑改成构建期生成代码。"Spring 魔法变少了"不是错觉,是工程化方向。
