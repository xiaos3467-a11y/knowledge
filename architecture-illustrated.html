第 一 讲

CAP:分区来临那天,你早就选好了

CAP 常被念歪。它的真身:C 一致性、A 可用性、P 分区容错——三者中 P 不是选择项,网络会坏是现实。所以你实际要做的只有 CP/AP:分区发生时,你要多数派拒绝服务保一致(CP),还是各写各的留可用性(CA 之实)。而且分区只影响被切断的那部分节点,没分区时系统仍可"又 C 又 A";粒度也可以拆——同一系统里,库存走 CP、朋友圈点赞走 AP。BASE(基本可用+软状态+最终一致)是 AP 阵营的工程纲领。

图 1三体集群 · 拉下"分区"闸刀,读一个刚被多数派改过的值

先写一笔再拉闸,Y 去读:CP 模式少数派侧直接拒绝并报 NoQuorum(你不在多数派里,不配回答);AP 模式愉快返回旧值 v=5 并标注"分区的另一侧也接受了写入 v=8,冲突等收敛"。ZK/etcd 站 CP,Eureka/Dynamo/Cassandra 站 AP;Quorum 的 W+R>N 就是"多数派"的连续旋钮。

要点追问"Redis 主从是 CP 还是 AP?"——异步复制天然偏 AP(主挂瞬间可能丢写);哨兵/Cluster 故障切换期间也不保证不丢——所以 Redis 做"效率锁"、做缓存,别做账本。能问出这句,CAP 这关算过了。

第 二 讲

入口层:哈希取模之痛,一致性哈希之解

无状态服务水平扩容随便加,但有状态的路由(本地缓存、连接粘滞、Redis Cluster 分片)遇到"加一台机器"就翻车:hash(key)%N 在 N 变成 N+1 时几乎所有键的归属都洗牌——缓存雪崩级打击。一致性哈希把键与节点都掷到同一个 0~360° 环上,键顺时针找最近节点:加节点只从它的"后继"手里接走一小段弧,删节点只交还自己那段——扰动从 100% 降到 1/N。虚拟节点(每物理点撒几十个小圆点)解决随机落点造成的负载不均,也让迁移更碎更平。

第 三 讲

限流:四种算法,一张流量对比图

限流是入口层的自保术:宁可拒掉 1%,也不能全服务 120% 累死。四代武功:固定窗口计数(实现 5 行,卡在窗口边界双峰:前一窗末+后一窗初,两倍流量穿透);滑动窗口(把窗口切成小格滚动,边界平滑,内存×格数);漏桶(请求进桶排队匀速漏出——强制恒速,想突发都不许);令牌桶(系统匀速造令牌,请求拿令牌走——允许攒着的突发,生产默认首选)。分布式限流再往上一层:中心化 Redis 计数器(精确但多一跳)vs 本地令牌桶+定期配额下发(高吞吐略糙,Sentinel 路子)。

点播放:同一段流量(平稳期 + 两波尖峰)同时喂给四种算法,配额都是 10/s。

尖峰①正好跨窗口边界:固定窗口放进 17 个(超配!),滑动窗口按小格滚动挡住;尖峰②持续短促:令牌桶靠攒的令牌放行一波(允许合理突发),漏桶把超出速率的一律滴掉(强制平滑)。没有最好的算法,只有你要的语义:保护下游用漏桶,容忍业务波峰用令牌桶。

第 四 讲

熔断、降级、隔离:让故障停在门外

限流防"量",熔断防"病":下游已经半死不活(超时/异常率飙升),还一个个请求送人头,会把线程池拖垮引发雪崩。熔断器就是保险丝:错误率过阈值 → OPEN 直接失败快速返回;冷却期后 HALF-OPEN 放几个探测请求;成功率达标才 CLOSED。降级是熔断后的"活法":缓存兜底、默认值、静态页、砍非核心功能(大促时关掉"猜你想看")。隔离是不让一锅烂:线程池/连接池按依赖分舱(舱壁模式)、队列分离、核心链路与非核心链路分集群。再往深一层是超时预算:整条调用链的超时逐跳递减,任何一跳不许吃掉全部时间——这比任何熔断器都更早救命。

图 4保险丝的一生 · 把下游拨坏,看状态机转一圈
CLOSED正常通行 · 统计错误率
OPEN快速失败 · 冷却计时

第 五 讲

分布式 ID:雪花算法的 63 个格子

分库分表后要全局唯一 ID,UUID 无序(第 4 册 MySQL 见过它的页分裂惨状)、DB 自增撑不住。雪花(Snowflake)把 64 bit 切成四段:符号位 1 | 毫秒时间戳 41 | 机器号 10 | 序列号 12——时间打高位所以趋势递增,同毫秒内用序列号自增补足,41 bit 管 69 年、10 bit 管 1024 台、12 bit 单机每毫秒 4096 个。三大软肋:时钟回拨(NTP 校时可能让时间倒退,要拒发/等待/借用备段位)、机器号要注册中心协调别撞、位段是零和分配——机器位多给一位,每毫秒容量就少一半。

图 5位段挪挪看 · 63 个格子,三重权衡一眼见底
可用年限69 年
最大节点数1024
单机每毫秒容量4096
全局每毫秒419 万
拖动滑块:总位数固定 63,时间戳每挪走一位,另两头就得还回来。

把时间戳砍到 30 位→年限只剩 3 年,但换来机器位 16 位(6.5 万节点)——这就是架构的"处处让渡"。工业变体:百度 UidGenerator(RingBuffer 预生成,解时钟问题)、美团 Leaf-segment(号段模式:DB 批量发号,服务内存消费,时钟回拨免疫)。

第 六 讲

MQ 可靠性账本:不丢、不重、防堆积

消息队列的三本账:不丢——生产端(本地消息表/事务消息把"落库"和"发消息"绑成同一原子)→ broker(副本+acks=all+刷盘策略)→ 消费端(先处理业务、后 ack,顺序反了等于用"丢消息"换"重复消息");不重——重试+网络抖动注定 at-least-once,幂等是消费端的天职(业务唯一键+去重表/Redis SETNX/数据库唯一索引);不堆积——消费者扩容、批量消费、堆积告警转储、最后的死信队列(DLQ)给人工兜底。顺序性:同一业务键路由同一队列(partition key),全局顺序基本是伪需求。

第 七 讲

多级缓存与一致性:快是真快,脏也是真脏

一台 Nginx/本地 Caffeine 的命中只需 百纳秒,Redis 一跳 约 0.5ms,回源 DB 5-20ms——把请求"层层截流",数据库才活得下去。但多一级缓存就多一个"数据副本"要过期:Cache Aside(旁路:读时回填,写时先落库再删缓存)是基线姿势;"先删再写"和"写库后不删"都会脏;延迟双删(写后延迟几百 ms 再补删一次)挡并发回填的旧值;终极正规军是 binlog 订阅(Canal)异步失效——把"删缓存"变成数据库变更的确定性下游,业务代码零侵入。

第 八 讲

分库分表:分片键的选择,和"基因"的补救

单表千万级、单库 IOPS 顶,就得上水平拆。分片键决定一切查询的形状:按 uid 哈希——用户维度丝滑,商家/时间维度变广播查询;按时间——写入均匀变热点写(当月分表独扛所有流量),老数据冷得快。常用折中:主路由按 uid 分库分表,异构一份按 merchant_id/时间 的索引表(或 ES/宽表)扛其余维度。分页是深坑:LIMIT 500,10 每个分片都要捞前 510 条再归并——N 个分片放大 N 倍。基因法(Gene)优雅补刀:订单号生成时把分库分表位"织"进末尾,拿订单号查详情不用知道 uid——路由信息自携带。

第 九 讲

分布式事务:2PC、TCC、Saga、本地消息表

一单跨三个服务,ACID 的 A 出了进程就没了。四件武器:2PC/XA——协调者两阶段(prepare 锁资源→commit),强一致但同步阻塞+协调者单点,prepare 后崩了参与者锁资源干等,微服务里基本判了缓刑;TCC——业务层的 Try(预留:冻结库存/额度)→ Confirm/Cancel 两刀,快且不锁 DB 连接,代价是三个服务要写三套接口,还要处理幂等/空回滚/悬挂;Saga——长事务拆成一串本地事务,失败就逆序执行补偿动作(退款、还库存):无资源预留、吞吐高,隔离性弱(中途别人能看到"半成品"状态);本地消息表/事务消息——不追求原子、只保证最终到达,MQ 扛重试,业务幂等收口——互联网量级的默认选择。口诀:能异步就消息表,要预留上 TCC,长流程用 Saga,2PC 留给真强一致的存量场景。

第 十 讲

高可用:从单机房到异地多活、单元化

故障是概率,架构是赔率:多副本消灭单点 → 同机房多可用区 → 同城双活(RPO≈0)→ 异地(延迟 30ms+ 写不过去,只能读扩散/单元化)。衡量标尺 RTO(业务能忍多久的不可用)/RPO(能忍丢多久的数据),它们直接换算预算。热切换的四大名捕:VIP/DNS 切流(GSLB)、数据同步延迟追平(DTS/DRC)、流量灰度回切、以及演练——没做过故障注入的"多活"只是 PPT 多活。单元化(Settlement)是终局思路:按 uid 尾号把"存储+计算+缓存"封成一个自给自足的单元,单元间不依赖,炸一个单元切 1/N 流量,故障域天然收敛。

图 10四级架构对比 · 按下"杭州机房起火"

同一个"起火了"按钮,四种架构四种剧本:单机房全黑 RTO 小时级;同城双活分钟级切流 RPO=0;异地灾备看同步延迟丢一段增量;单元化只损失一个单元的流量+对应数据分片,爆炸半径 = 1/5。追问"为什么异地不直接双写?"——30ms 往返 × 强一致 = 写延迟翻几十倍,鱼与熊掌。

第 十一 讲

可观测性:一次请求的 CT 片

Metrics(聚合的病历:错误率 0.4%、P99 800ms)、Logs(细节的切片,查单条用)、Traces(把一次请求跨 N 个服务的因果链缝起来)——三支柱由浅入深。Trace 三要素:traceId 全局唯一贯穿始终,spanId+parentSpanId 拼出调用树,W3C traceparent header 让网关/服务/MQ 消息都带着它走。采样别只抽 1%:全量保留错误与慢请求,正常流量才降采样。OpenTelemetry 已经是事实标准:一个 SDK 同时喂 trace、metric、log 三张嘴,且用关联 id 把三者钉在一起——从告警点进 trace,从 span 跳到日志,这叫可观测,否则只是三堆监控数据。

第 十二 讲

背封装订:两分钟给一个系统估出机器数

架构师面试与工作的基本功——数量级估算。规则常数先钉牢:内存访问 ~100ns / SSD 随机读 ~100µs / 磁盘寻道 ~10ms / 内网 RTT ~0.5ms / 同区域跨可用区 RTT ~1ms / 跨国 RTT ~150ms;单核简单请求 ~10k QPS;日志/详情按 DAU × 人均次数 × 条大小 × 留存期三行算完。流程:DAU → QPS(均值=日请求/86400,峰值×2~3 倍)→ 读写比 → 存储 → 实例数(向上取整+冗余 2 台起)。估的是数量级,不是报价;把每张假设摆出来,评审才有靶子可打。

第 十三 讲(终)

架构是权衡,不是清单

同一个"订单系统",金融、社交、秒杀会给出三套几乎不相交的架构:一致性、可用性、性能、成本是互相挤压的四角,业务定位决定谁让路。工程判断的通用姿势:① 先定义不可妥协项(资损=0 还是 3 个 9?);② 从最简方案起步,拿度量数据说话再复杂化("需要上 MQ 吗"→ 先看下游是不是秒级消费就够);③ 每个选择写 ADR:场景、选项、决定、代价;④ 演进式设计——为明天的规模设计,为今天的复杂度买单。

图 13三个业务,三张取舍表 · 点卡片看四角怎么让位

核心差异记三句:支付选 C 舍 A(宁可超时不可错账),信息流选 A 舍 C(少刷一条比刷不出强),秒杀本质是"用入口截流保住后端,把一致性推迟到异步"(库存预扣 Redis 原子 + MQ 落库 + 支付超时释放)。架构面试终极模板:先摆约束,再列选项与代价,最后给"我选什么+为什么"。
