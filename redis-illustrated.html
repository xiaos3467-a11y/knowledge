第 一 讲

Redis 是什么,凭什么快

Redis(Remote Dictionary Server)是一个运行在内存里的键值数据库。单机就能稳拿约 10 万 QPS 的量级,而一次带磁盘访问的 MySQL 点查往往要 5–20ms——这是它成为"缓存"代名词的根本原因。常见用途:热点缓存、计数器、排行榜、分布式锁、会话共享、消息(Stream)、地理位置(GEO)、布隆去重。

图 1取一条数据:内存航班 vs 磁盘航班

—
MySQL · 读磁盘

① 全在内存读写字节级代价,磁盘要寻道、读页,慢几个数量级
② 单线程执行命令没有锁竞争、没有线程上下文切换,见第 2 讲
③ IO 多路复用一个 epoll 照看几万条连接,见第 2 讲
④ 高效数据结构SDS / listpack / 跳表 / 压缩整数集合,见第 3、4 讲
动画放大了真实比例:0.2ms 对 10ms,正好差 约 50 倍

同一个"读一条记录",内存里是一次指针的旅程;磁盘上是一次磁头的旅程。Redis 的快,首先是存储介质的快。

要点Redis 不是"更快的 MySQL",它是另一层的系统:数据先在内存里被命中,数据库只是兜底。理解后面所有章节,都可以带着这个问题去看——这一步省掉的是网络往返,还是磁盘 IO?

第 二 讲

单线程事件循环:它真的"单线程"吗

一条命令在 Redis 里的一生:客户端 socket 就绪 → IO 多路复用器(epoll)感知 → 从队列里取出命令 → 单线程逐条执行 → 写回回复。Redis 6.0 引入的"多线程"只负责网络读写与协议解析,命令的执行仍然是一个线程——所以"Redis 是单线程模型"这句话,指的从来是执行。

为什么单线程反而快?因为 Redis 的瓶颈在内存和网络,不在 CPU:省掉了线程切换和加锁开销,每个请求走"快速路径"。也正因为串行,任何一条命令都没有并发执行的对手——单条命令天然原子;但反过来,一条慢命令就会堵住所有人。

三盏灯是事件循环的一轮:读取 → 执行 → 回复,永远串行。慢命令进场的瞬间,它身后所有请求的等待时间一起变长——这就是线上禁用 KEYS 的理由。

把慢命令逐出事件循环

  • 用渐进式遍历 SCAN / HSCAN / SSCAN / ZSCAN 替代 KEYS、HGETALL 大 hash;
  • 大集合排序交给 SORT RO 或应用层;删大 key 用 UNLINK(后台线程回收内存);FLUSHALL ASYNC;
  • 开 maxmemory 与慢日志 SLOWLOG GET 抓现行;7.0 的 io-threads-do-reads 与命令批量执行(fstacked)进一步摊薄 IO 开销。
想一想:第 2 讲说"单条命令天然原子",那第 11 讲为什么还需要 MULTI 事务和 Lua?——因为原子的是"一条命令",不是"一串命令读同一个 key 的整个过程"。

第 三 讲

五大数据类型:每种都有自己的"小身子骨"

Redis 的类型不是"表结构",而是为不同形状的数据选了不同的底层编码。小数据用紧凑的连续内存(listpack/intset,省内存、缓存友好),超过阈值自动转成指针结构(hashtable 等)。下面这个"类型台"可以逐个打开看,还能往里塞数据、亲眼触发编码转换。

图 3类型控制台 · 点标签切换,点按钮动手

左侧是当前类型的微观结构与交互实验,右侧是这个类型最常用的命令。编码转换阈值(hash-max-listpack-entries=128 等)在实验里被缩小到 12,方便你几秒内看到"变身"。

这一讲的记忆锚点

  • String 底层是 SDS 动态字符串:O(1) 取长度、预分配 + 惰性释放减少 realloc、二进制安全(可以存图片)。value 小于 44 字节用 embstr(一次分配),纯数字用 int 共享对象,否则 raw。最大 512MB。
  • List 底层是 quicklist:双向链表,每个节点装一个 listpack(7.2 起取代 ziplist,修复了连锁更新隐患)。两头进出一律 O(1),中间按索引访问是 O(N)——别拿它当随机访问数组用。
  • Hash:字段少而小时整个 hash 挤在一个 listpack 里(没有指针开销,配置对象的首选);大了转 hashtable,字段多而 value 大时还能启用 hash 的 zval 共享编码省内存。
  • Set:全是整数且 ≤512 个 → intset 有序数组;否则 hashtable。交并差 SINTER / SUNION / SDIFF、共同好友、抽奖 SPOP、随机采样 SRANDMEMBER。
  • ZSet:小 → listpack;大 → dict + skiplist 双结构:dict 管"成员→分数"O(1) 查分,跳表管排序取名次。下一讲专拆它。
要点被问"底层用了什么数据结构",标准答法是分大小说:小对象 listpack/intset,超过阈值转 hashtable/skiplist,阈值来自 hash-max-listpack-entries、zset-max-listpack-entries 这些配置——一句话里既有结论又有调优意识。

第 四 讲

跳表:一条随机的"快速路"

跳表(skiplist)就是给有序链表加了几层"高速路入口":每个节点抛硬币决定自己长多高(Redis 里晋级概率 p=1/4,最高 32 层)。查找时从最高层出发,能走就走、走过头就下楼,平均每比较 log1/pN ≈ 2·log₄N 次命中目标,O(logN)。

ZSet 为什么选跳表而不是红黑树?① 好写好懂,没有旋转的复杂度;② 范围查询太顺——最底层就是完整有序链表,ZRANGEBYSCORE 找到起点直接往后串;红黑树做区间要先找 LCA 再中序遍历;③ 概率平衡不需要严格再平衡;④ 内存换时间可控(每节点平均 1.33 个指针)。代价:没有 dict 的 O(1) 查分,所以 ZSet 是 skiplist + dict 两个结构共享成员——排名找跳表,查分找 dict。

比较次数 —若用普通链表 —节点指针均值 ≈1.33 · 层高上限 32
查找成员分数(=节点值): 每步动画后自动讲解;找不到时指针停在"应该插入的位置"前

第 五 讲

持久化:RDB 快照与 AOF 日志

内存说没就没,所以 Redis 要把数据落到磁盘。RDB 是"照一张全景照片",AOF 是"记一本流水账":RDB(SAVE/BGSAVE)在某个时刻把全部键值序列化进 dump.rdb;BGSAVE 会 fork 一个子进程去写盘,靠操作系统的写时复制(COW)让父子共享同一份内存,只有被改写的页才复制。

AOF(appendonly yes)把每条写命令追加进 appendonly.aof,重启时"重放日志"恢复。日志先写进 aof_buf 缓冲区,由 appendfsync 决定何时刷盘:always 每命令一次(最稳最慢)、everysec 每秒一次(默认,最多丢 1 秒)、no 交给操作系统(最快,可能丢很多)。AOF 越记越长,超过阈值后 fork 子进程做重写——用当前内存状态生成最小命令集,而不是回放历史。

第 六 讲

过期与内存淘汰:两套"清道夫"

Redis 的过期靠惰性删除 + 定期删除两条腿:设过 EXPIRE 的键记在 expires 字典里;访问一个键先查它是否过期,过期就当场删(惰性,CPU 友好但可能占着内存不还);后台每 100ms 跑一次定期任务——从带 TTL 的键里随机抽 20 个,删掉其中已过期的,若过期比例超过 25% 就立刻再来一轮(上限 1ms 时间片,防止把主循环拖死)。

当内存达到 maxmemory,就是另一套故事——淘汰策略(maxmemory-policy):8 选 1,按"从哪些键里挑"(全部/只挑设过 TTL 的)与"怎么挑"(LRU/LFU/TTL/随机/noeviction)组合。精确 LRU 要维护全量链表,太贵;Redis 用采样近似:随机抽 maxmemory-samples(默认 5)个,淘汰其中最久未用的——用一点点误差换 O(1) 的开销。Redis 4.0 加了 LFU:每个对象 8 bit 计数器,对数概率递增 + 随时间衰减,专治"偶尔一次被访问就赖着不走"。

第 七 讲

缓存三大问题:穿透、击穿、雪崩

三个词长得像,病因完全不同:穿透是查的键根本不存在,缓存里永远没有它的坑,次次漏到 DB;击穿(局部失效)是一个热点键过期瞬间被并发打穿;雪崩(全局失效)是一大批键同时到期(或 Redis 整个挂了),流量像雪崩压向数据库。三句话,三个解法方向:防不存在、防单点瞬间、防同一时刻。

图 8三大问题彩排台 · 选剧本开演,再开解法重演一遍

青色 = 缓存命中直接返回;琥珀/红色 = 请求漏到底层数据库。右下角的仪表是 DB 负载——三大问题的共同终点都是把它打爆,解法的共同终点都是把它按下去。

成因解法(按优先级)
缓存穿透查询不存在的数据 / 恶意随机 key① 参数合法性校验挡在门外 ② 缓存空值(短 TTL)③ 布隆过滤器前置(注意:标准 bloom 不支持删除,误判率要按容量算)
缓存击穿单个热点键过期 + 高并发① 互斥重建:只放一个请求去 DB,其余等待/降级 ② 逻辑过期:值里带过期时间,过期先返回旧值、异步刷新(热点 key 干脆不设物理 TTL)
缓存雪崩大批 key 同一时刻过期;或 Redis 服务整体不可用① TTL 加随机抖动打散 ② 多级缓存(本地 Caffeine 垫一层)③ 网关限流/熔断兜底 ④ 高可用:主从 + 哨兵/Cluster(八九十讲)把"整体挂"的概率压下去
想一想:雪崩的终极解法为什么是"高可用 + 限流"而不是"永不过期"?——缓存的价值在于能失效;不能失效的缓存,是把自己写成了数据库。

第 八 讲

主从复制:全量与增量

副本要跟上主库,分两种剧本。全量复制(第一次见面):副本发 PSYNC ? -1,主库 BGSAVE 生成 RDB 并流式推送,副本落盘加载;传输期间的新写命令暂存在副本客户端输出缓冲(client-output-buffer-limit slave 256MB 64MB 60s——缓冲爆了就重来,大实例要么调大要么用无盘复制 repl-diskless-sync)。加载完主库把缓冲里的命令倾泻而下,追平后进入命令传播:长连接,一条命令一条命令地推。

部分(增量)复制(短暂断线):每个主库有一个 ID(replid)和一个递增的 复制偏移量 offset,副本记录自己复制到哪;主库把最近发过的命令写进一块环形 backlog(默认 1MB)。重连时副本报上 replid+offset,缺口还躺在 backlog 里 → 只补发差的那一段;断太久、缺口被覆盖 → 退回全量。主库故障切换后 replid 换新,只带 replid2 能对上号的副本才能走增量。

要点主从的三大意义:热备(数据冗余)、读扩展(读多写少的流量分给副本)、Cluster 的地基(每个分片就是一主一从)。追问必到:主从是强一致吗?——不是。复制是异步的,副本可能读到旧数据;Redis 没有提供"写成功即所有副本可见"的同步写语义,WAIT 命令只能"尽力等待"。

第 九 讲

哨兵:给主从加一双"盯梢的眼"

主从解决了"有备胎",没解决"备胎自动上位"。Sentinel(哨兵)集群干的就是这件事:监控、通知、自动故障转移、为新主库配置。每个哨兵每秒 ping 主库、副本和其他哨兵;超时判主观下线(SDOWN,"我觉得它死了");再把判断广播给同伴,达到 quorum 个哨兵都说死,才升级为客观下线(ODOWN)——防止一个哨兵网抖误判。

确认主库真死后,哨兵们先选一个领头哨兵(类 Raft:configEpoch + 过半同意)来主持葬礼兼婚礼;领头者从副本里挑新主:过滤掉下线的、断线的 → slave-priority 优先级高者 → 复制 offset 最新者 → runid 最小者。然后让其他副本 REPLICAOF 新主,老主复活也只能当副本,最后通过发布订阅把"换主了"通知给客户端。

要点哨兵部署至少 3 个、奇数、分散在故障域(不同机器/可用区)。哨兵保存配置靠"订阅 +1/-1 计数器"彼此对齐,老主复活会收到新主的 REPLICAOF 指令——所以哨兵模式里老主绝不会双写。哨兵只管"一主 N 从"这一组,想要横向扩容看下一讲的 Cluster。

第 十 讲

Cluster:16384 个槽的三国时代

哨兵再稳,写也集中在一个主库。Redis Cluster 把键空间切成 16384 个哈希槽(hash slot),分给 N 个主库各管一段:slot = CRC16(key) % 16384。每个主库再带自己的副本,分片内主挂了分片内切换——又扩容、又高可用。为什么是 16384 而不是 65536?心跳包要把"每个槽属于谁"的位图发给所有节点:16384 位 = 2KB,65536 位 = 8KB,心跳开销乘以节点数;而常见部署不超过一千个主节点,16384 够分。

客户端可能拿不到准确的槽表,于是有了两种重定向:MOVED(槽有固定主人,你问错了节点,直接告诉你去谁那,客户端可缓存修正)和 ASK(槽正在迁移中,这条请求去临时接收方碰运气)。想多键操作同槽,用 hash tag:{user:1001}.name 与 {user:1001}.age 只对花括号内容做哈希,天然同槽。

foo 落在 12182、bar 落在 5061(可与真库 CLUSTER KEYSLOT 对答案)。连续点两个 {user:1001}.* ——花括号里的内容相同,槽必然相同,这才 MULTI/Lua 多键在集群里的活路。点"💥 M3 宕了":它的副本 S3 就地升主,槽表无缝接管,路由照常。

要点节点间靠 Gossip 协议(ping/pong 心跳)互相感知状态、传播槽表;多数主节点认为某分片主不可达,分片副本才升主。Cluster 的 Lua/MULTI 只允许操作落在同一槽的键;副本读的是"大概最新"——读写分离要接受这个语义。集群无跨槽再平衡的手动干预成本,扩容用 redis-cli --cluster reshard 在线搬槽。

第 十一 讲

事务与管道:打包的艺术

事务(MULTI/EXEC):把一串命令排队,EXEC 时一次性串行执行,中间不插别人的命令——这是"隔离"不是"回滚":入队时语法错误会拒绝整个事务,但执行期错误(比如对字符串 INCR)之后的命令照样执行,已执行的不撤销,不满足 ACID 的 A。WATCH 提供乐观锁:被监视的键在 EXEC 前变了,事务直接放弃返回 (nil),客户端重试。

管道(Pipeline):纯粹省网络——把 N 条命令一次发出去、一次性收回复,把 N 次 RTT 压成 1 次。它不提供任何原子性保证——服务端还是一条条执行,别的事务穿插照样穿插。事务管"逻辑上打包",管道管"网络上打包",这题面试最爱挖坑。

第 十二 讲

分布式锁:一把锁的四个灵魂拷问

SET lock <uuid> NX EX 30 一行就是 Redis 锁的全部入场式:NX 保证互斥,EX 防死锁。但真正的工程在四个追问里——① 会不会死锁?超时有 TTL,但要显著大于业务最坏耗时。② 会不会误删?value 存唯一标识,释放时先比对——而且"比对 + 删除"必须 Lua 原子完成,否则"我查完是我的,还没删就过期被别人拿了"。③ 业务没干完锁先过期怎么办?看门狗(如 Redisson)在持有期间周期续期。④ 主从切换丢锁怎么办?主库刚加锁就宕机、锁还没复制到副本就升主——锁凭空消失。RedLock(向 N 个独立实例多数加锁)想治这个病,但它对时钟漂移和进程停顿的依赖争议很大(Martin Kleppmann 的批评),强正确性场景(钱)请改用数据库行锁/共识系统,Redis 锁更适合"效率锁"——减少冲突,而非绝对的排他。

要点面试收口句:"Redis 单实例锁在极端故障下不保证互斥,所以它适合做效率锁;做正确性锁要么 Redlock + 充分认知其局限,要么换方案(数据库乐观锁、ZooKeeper/etcd 的临时顺序节点 + 会话机制)。"——能说出"效率锁/正确性锁"这组对比,这题就赢了。
