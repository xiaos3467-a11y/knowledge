虚拟机 · 十一讲

JVM
图解讲义

一把能拉动的内存标尺:-Xmx 一改,堆里新生代/老年生的份额、方法区与每根线程栈的开销随之重排——先对手感,再讲原理。

序JVM 进程内存全景 · 拉这两个滑块

堆只是 JVM 内存的一部分:每根线程还有 1MB 的虚拟机栈(200 线程=200MB!),Metaspace 在堆外。生产上"堆设多大"之前先算清"进程总共要吃多少"——Xmx + Metaspace + 线程×栈 + 直接内存 + GC/JIT 自身开销。

第 一 讲

运行时数据区:五块地的归属

线程私有三块:程序计数器(当前字节码行号,唯一不 OOM 的区域)、虚拟机栈(每方法一帧:局部变量表/操作数栈/动态链接/返回地址)、本地方法栈。线程共享两块:堆(对象们,GC 主战场)、方法区(JDK8 起用 Metaspace 实现:类元数据+运行时常量池;字符串常量表和静态变量随类走,HotSpot 里其实放堆中)。堆里再分代:Eden + 两个 Survivor + 老年代,默认 8:1:1。

异常对号入座:栈太深→StackOverflowError;堆尽→OutOfMemoryError: Java heap space;类加载不止→OOM: Metaspace;DirectByteBuffer→Direct buffer memory。

第 二 讲

对象的一生:分配、布局、对齐

new 一个对象:TLAB(每线程私有分配缓冲,免锁)里指针碰撞切一块(内存规整时)或空闲列表找洞(碎片多时)。对象本体三段式:Mark Word(hashcode/GC 年龄/锁状态——第 3 册锁升级的开关就埋在这 8 字节)、类型指针、实例数据,末尾填充对齐到 8 字节的倍数。开了压缩类指针(默认,<32GB 堆),类型指针 8→4B,整对象普遍省 40%——这也是"堆别过 32G"传说的由来(跨过 32G 压缩失效,可用内存反而可能倒退)。

图 2User{long id; int age;} 的字节解剖 · 开关压缩指针
对象总大小 24B

long(8)+int(4)=12B 数据,但对象头 12B+填充 4B → 24B。空对象也要 16 字节——所以"用一百个小对象攒缓存"往往不如一个大数组。空闲列表模式下,点它看 CMS 碎片的分配方式(找洞→切块→剩洞)。

第 三 讲

死活判定与四种引用强度

Java 不用引用计数判死(循环引用直接判不了:a↔b 互指,各自归零却永远回收不掉——图中演一遍),用可达性分析:从 GC Roots(栈上引用、静态变量、常量、JNI、活线程…)出发遍历,走不到的即死。四种引用是一档档"求生的姿态":强引用宁死不回收;软引用内存紧张时最后一捞(缓存);弱引用下次 GC 必回收(ThreadLocalMap 的 key!);虚引用等于没引用,只为回收时收张回执(清理堆外内存)。

第 四 讲

四种收集器:一场"搬球赛"

回收就两步:标记存活 → 整理/清理。Serial=一个人搬(暂停长,客户端默认);Parallel=四个人一起搬(吞吐优先,堆不太大的批处理服务首选,JDK8 默认);CMS=应用程序和保洁员并发干活(标记阶段业务照跑,只最后短暂 remark),但不整理 → 碎片,碎片塞不下大对象就退化成 Serial Old 大长脸,且并发阶段用户线程还在造垃圾——浮动垃圾+Concurrent Mode Failure 是它的病根;G1=把堆划成 Region 网格,每次挑"垃圾最多"的几格回收(-XX:MaxGCPauseMillis 给个暂停预算,回收计划按预期收益排优先级)——大堆(6G+)低延迟通吃的现代默认,ZGC/Shenandoah 再把暂停压到亚毫秒(着色指针/读屏障,几乎与堆大小无关)。

第 五 讲

分代假说与对象的一生

分代赌的是弱分代假说:越新的对象越容易死。对象生在 Eden;minor GC 活下来的进 Survivor(from↔to 每次翻转,不复制不整理),年龄 +1;到阈值(默认 15)晋升老年代。三个插队机制:动态年龄判定(同龄总和>Survivor 一半,≥该年龄直接晋升)、大对象直入老年(避免在 Survivor 间搬砖)、空间分配担保(老年剩余<历次晋升均值→提前 Full GC)。老年代满=Full GC:全堆扫描+整理,长暂停之源。

按剧本连按:几轮 minor 后 Survivor 越来越挤→动态年龄→晋升加速→老年水位爬升→Full GC 长暂停。"线上偶发卡顿"的案底,多半就在这条水位线上。

第 六 讲

卡表:跨代引用的记账本

minor GC 只想扫年轻代,可老年代对象可能指着年轻代(跨代引用)——不把老年代全扫一遍,怎么知道哪些 young 对象还活着?答案:卡表(Card Table)。堆按 512B 切"卡",老年代对象写一个年轻代引用时,写屏障顺手把对应卡标"脏"(一条机器指令的事)。minor GC 时:GC Roots + 脏卡里的老年对象一起当根,老年代本体免扫。一次写开销,换全堆免扫——用空间(512 卡:1 字节省时间)的典范。G1 在此基础上加 RSet(反向表:谁指着我),换 Mixed GC 时免扫他区。

第 七 讲

类加载五阶段与双亲委派

一个类进入 JVM 要过五关:加载(全限定名→字节码→方法区元数据+堆中 Class 对象)→ 验证(文件格式/元数据/字节码/符号引用四道安检)→ 准备(静态变量分配内存给零值——static int x=7 此刻 x 还是 0,7 在初始化阶段才写;但 static final int X=7 编译期常量直接上)→ 解析(符号引用→直接引用)→ 初始化(执行 <clinit>:静态赋值+静态块,父类先行,JVM 保证线程安全——单例的"静态内部类"写法就赌这个)。

双亲委派:收到加载请求先向上问(App→Platform(9 前叫 Ext)→Bootstrap),父能加载则child不动手;父都不行才自己load。收益:核心类不被篡改(你写个 java.lang.String 永远轮不到加载)、复用不重复。破功现场:SPI(JDBC)要"父接口、子实现",用线程上下文类加载器反委派;Tomcat 每应用一 Loader 优先自载(webapp 隔离);OSGi/9 的模块也是受控破坏。

图 7五关打卡 + 委派链实测 · 换个类名问一次

String:一路向上,Bootstrap 亲自出手 Biz:三层都摇头,App 自己 load;SPI:Bootstrap 的 DriverManager 用线程上下文加载器反向摸到 jar 里的实现——委派是主干,破例处皆是场景题。

第 八 讲

调优四场景:先对症,再开药

调优第一原则:没有指标不动手。四张常见病卡(点开看诊断路径):Full GC 频繁、单次 STW 过长、OOM 现场、CPU 全红。参数不求多,记住主线:-Xms=-Xmx 免抖动、堆大小给足但留非堆余量、先选对收集器再微调(大堆低延迟 G1/ZGC,吞吐批处理 Parallel)、GC 日志常开(-Xlog:gc*)。

第 十 讲

JIT:热点变机器码,对象可以"不存在"

Java 半解释半编译:方法越热,分层编译越往上爬——解释器起步(启动快)、C1(简单编译+profiling 埋点)、C2(按热度画像激进优化:内联、逃逸分析、锁消除、标量替换)。所以"跑热了才快",预热/压测差一个数量级是常态。逃逸分析最魔幻:方法里 new 的对象若从不逃出(不被返回/存静态/作参数漏出去),根本不在堆上实例化——拆成寄存器里的标量,栈帧退场即销毁,连 GC 都省了。"别为 new 对象纠结,尽量方法内造小对象"的现代依据就在这。

第 十一 讲

容器里的 JVM:你以为的内存不是你的

老 JDK(8u131 前无容器感知)在容器里看的是宿主机资源:8C32G 的机子给 512M limit 的容器,JVM 照宿主机算默认堆(1/4=8G!)、GC 线程数、JIT 编译线程——水位一路涨到 cgroup 红线,内核直接 SIGKILL,事件日志只有 Exit 137,连 OOM 异常都来不及抛。现代方案:8u191+/10 默认 UseContainerSupport 读 cgroup limit,或用 -XX:MaxRAMPercentage=75 按百分比留头寸;CPU 同理限 ActiveProcessorCount。第二课:堆内泄漏 JVM 会自己抛 OOM 给你堆转储,堆外(DirectBuffer/Mmap/native 库)超限是容器杀进程——两种死法现场完全不同,排查路线也不同。
