第 一 讲

Pod:为什么不直接管容器

Docker 管容器,K8s 管 Pod——因为"一组必须同生共死、共享 localhost 与磁盘的容器"才是调度的自然单位:主应用+日志 sidecar、应用+envoy 数据面、初始化容器(initContainers 按序跑完才开门)。同 Pod 容器共享网络栈(同一个 IP!)和 volume,跨 Pod 只能通过 Service 对话——这条边界就是"进程组"的容器化转世。一个 Pod 一个 IP 让"localhost 直连 sidecar"零成本;也解释了为什么 Pod 是临时牲口:重建后 IP 换人——所有"按 Pod IP 找服务"的想法都该被 Service 接走(第 3 讲)。

图 1解剖一只 Pod · 点容器看共享了什么

答"能不能互通":能——同一 netns;但跨 Pod 的 localhost 谁也见不着谁。K8s 世界没有"绕过主机网络"的魔法,只有把"协作关系"显式声明成 Pod 边界,这也是 sidecar 模式的物理基础。

第 二 讲

控制器模式:期望状态与调和循环

K8s 没有"执行命令",只有"改期望+看现实"。每个控制器都是一个死循环:watch spec 与 status 的差异 → 有差就动手抹平 → 再看(reconcile)。你从来不需要"重启 Pod",你只需要把 replicas: 3 写进 spec,Deployment/ReplicaSet 控制器自会把现实掰成 3 个——节点挂了也一样。三大工作负载的分工:Deployment(无状态、随便杀、滚动升级)、StatefulSet(有身份:pod-0/1/2 稳定序号+稳定存储+按序启停,给数据库/集群中间件)、DaemonSet(每节点一个,日志/监控 agent)。

"删 Pod"在 K8s 里不是故障,是常态输入——控制器的存在就是让"少了一个"这个现实永远够不到"3 个"这个期望。

声明式带来的超级能力:自愈(故障=现实偏离期望,自动补)、可审计(YAML 就是文档)、可回滚(Rollout 历史)。命令式脚本"重启第 3 台机器"在 K8s 里没有意义——机器本来就没有第 3 台。

第 三 讲

Service:给牲口发工牌

Pod 是临时 IP 的牲口,Service 给一组 Pod(label selector 圈定)发一个稳定的访问入口:ClusterIP(虚拟 IP,iptables/IPVS 把流量随机洗到后端 Pod)、NodePort(每个节点开端口)、LoadBalancer(云厂商 LB)、Inress(七层域名/路径路由,统一入口的看门人)。DNS 是 Service 的白送名:order-svc.ns.svc.cluster.local——服务发现就这么土法 yet 优雅。headless(clusterIP: None)直接返回 Pod IP 列表,给 StatefulSet 的"点名访问"用。网络四层口诀:Pod 网(CNI,跨节点扁平)、Service 网(虚拟 IP)、Node 网、外部(LB/Ingress)——面试"从 curl 到 Pod 走了几步"就是把这四层串一遍。

图 3一次服务调用的路由 · 多打几次看负载均衡
调用方永远只认 order-svc:443,不认识任何 Pod。

烧 Pod 剧本:Endpoint 列表(由 kube-proxy/EndpointSlice 自动维护)把死的摘掉、新 IP 补上——调用方零感知。K8s 网络的全部哲学:让"谁在那"变成动态清单,让"找谁"变成固定名字。

第 四 讲

PV·PVC 与 StatefulSet:数据的钉子户

Pod 是牲口,数据不能跟着死。PVC 是"存储需求申请单"(要多大、什么访问模式、哪类性能),PV 是集群里真实存在的卷;两者由"绑定"撮合;StorageClass 让 PV 可以动态 Provision——申请单一交,云盘自动造出来再绑定,运维不用手工登记。StatefulSet 再补上"身份":pod-0/pod-1/pod-2 稳定名字 + volumeClaimTemplates 让每个序号绑定自己专属的 PVC——pod-2 重建后还挂它原来的盘。MySQL 主从/Kafka/ZK 上 K8s 的全部前提就是这一条:计算可以死,盘的归属不能乱。

图 4申请单-货架-绑定 · 再看 pod-2 的"转世还认这块盘"

转世版:pod-2 名字没变、序号没变、绑定的 PVC/data 盘也没变——StatefulSet 的"S"就是这份稳定。Deployment 的世界没有这待遇:每个副本无身份,盘只能共享或没有。

第 五 讲

三探针与优雅下线:别让流量踩进坟场

三种探针管三件事:startupProbe(老慢启动的免死金牌——在它成功前,liveness 不作数)、readinessProbe(就绪没?"没就绪只是摘流量,不杀你")、livenessProbe(还活着吗?"死循环/假死就重启")。三者语义混用是事故温床:把 readiness 写成 liveness,依赖抖一下整个 Pod 被重启,雪上加霜。优雅下线时序:删除指令 → 同时(a)EndpointSlice 摘除流量(b)执行 preStop 钩子 → 给进程发 SIGTERM → 应用 graceful shutdown 收完在途 → 超过 terminationGracePeriod 仍不退场就 SIGKILL。preStop 里那几秒 sleep 不是玄学:是给"摘流量"在几十毫秒~秒级的传播异步性兜底,不然最后 1% 请求踩进已关门的 Pod。

图 5一个 Pod 的一生剧本 · 按时间轴放

正常剧本注意两个红叉的顺序:先摘流量、再 SIGTERM;病态剧本:连续 3 次失败 → kill → 重启 backoff。"为什么每次发版丢几个请求"——十有八九是没配 preStop/grace 的时序空档。

第 六 讲

requests/limits、QoS 与自动扩缩

两个字段三种人生:requests=调度时的预算账(节点剩余必须装得下)、limits=运行天花板(CPU 超了限流,内存超了OOMKill)。由此定出 QoS 三档:Guaranteed(request=limit,驱逐最后动你)、Burstable(给了 request)、BestEffort(裸奔,节点内存紧张第一个被杀)。生产大忌:不设 requests(调度瞎蒙)或只设 limit 不设 request(超卖狂魔)。HPA 则把"目标 CPU 均值"翻译成副本数:metrics-server 供数 → 公式 desired=current×(util/target) → 扩到上限;它是周期拉取+限流变化速率的慢反馈,扛突发流量还得VPA/KEDA(按队列长度扩)/上游限流组合。

图 6加压 → HPA 响应 · 顺便把 requests 撤了看调度变傻

70%>50% → HPA 把副本 3→5 摊薄压力 → CPU 回落 → 缩容要过"稳定窗口"(默认 5min,防抖动)。HPA 调的是副本数不是规格;扩得动的前提是节点池还有机器(那该问 Cluster Autoscaler)——三层弹性的链条别断在最底下。

第 七 讲(终)

控制面全家福:kubectl apply 之后发生了什么

收官把所有角色叫齐。控制面:kube-apiserver(唯一入口:认证→鉴权→Admission→写 etcd,无状态可扩)、etcd(集群唯一的真相,一份 KV)、scheduler(watch 无家可归的 Pod,过滤+打分写 binding)、controller-manager(几十个调和循环住在一起)。每个节点上的数据面:kubelet(管 Pod 生死、跑探针、上报状态)、kube-proxy(Service 转发的规则执行者)、CNI 插件(给 Pod 发 IP 连隧道,Calico/ Cilium 们)。全链路广播机制是 watch:一切组件都是 apiserver 的订阅者——这就是 K8s 只"声明+观察",从不"命令"的技术底座。
